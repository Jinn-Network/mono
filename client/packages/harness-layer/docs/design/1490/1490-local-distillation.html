Surface 1 · jinn-agent CLI

Local distillation — consent, control & run

Rung 1: distil your own local task captures with a frontier-class model into reusable skills, then run later tasks cheaper on a small open-weight model. This surface is the consent for that spend, the persistent where it runs control — local / defer / off — and the terminal view of what a run produced. Distillation is a heavy local pass, so you decide whether and where it happens. Reuses the #1312 consent pattern and #1319 splash conventions; nothing new is invented.

Consent & where it runs — interactive

Walk it with the keyboard (click the console first). It leads with what distillation is for — distil once, run cheap forever — then states plainly what it reads, what it costs (compute, not money), and what leaves the machine (nothing). The action lifecycle is idle → confirming → recorded, shown bottom-left. Three modes: local runs now (a spend, so it confirms), defer holds captures for later, off stops reserving them. Default on bare Enter is defer — the mode that spends nothing and publishes nothing. Jump to any state with the chips.

Persistent mode & the deferred path

The where it runs mode is a setting, not an interactive-only prompt — set it with a flag from any script. And when the mode is defer, a bare jinn-agent distil does nothing but say so: captures are held locally, nothing runs, nothing is published. That is the placeholder for the rung-3 signal path — the point where the bonded network could one day distil a contributed signal, with its own consent, out of scope here.

Design notes — 1490 local distillation

Two consents, one register

#1312 governs data leaving the machine — publishing a scrubbed trace to a public corpus. #1490 governs a spend on the machine — a heavy frontier pass over local captures whose output stays local. Different risk, same rule: drop the metaphor whenever cost is on the line. So this screen never says summon or smoke; it says "heavy compute, not money", "nothing is sent to a provider", "nothing is published to the Jinn network". Vow-language returns only in neutral chrome — the ◇ skill signal line, the run's scrying.

  • Lead with the upside, flatly. Distil once, run cheap forever — the arbitrage is the headline, stated clinically. No urgency, no exclamation.
  • The distiller is the operator's choice. A local frontier-class model is the default, so "nothing leaves the machine" is literally true; the consent screen and preview both show it can be changed with --distiller, and name the one case that isn't local — a hosted model — with a promise to ask before the first send. We do not bury it.
  • Confirm only the spend. local costs compute, so it takes a deliberate Y/N. defer and off spend nothing and record directly — no friction where there is no cost.

Where it runs — local · defer · off

ModeRuns a frontier pass?Captures kept?Anything published?
localYes — now, on this machine.Yes — read, then distilled.No. Skills stay local.
defer (default)No.Yes — held locally, untouched.No. Rung-3 placeholder only.
offNo.No — not reserved for distillation.No.

Default is defer because it is the mode that changes nothing: no spend, no publish, and captures are the harness's normal task records either way. off is the only mode that stops reserving captures, so it is a deliberate choice, not a default.

Run output — shape

  • Progress is legible, not chatty. One header line (mode · distiller · capture count), one progress line (4 of 6 · ~3 min left), then a per-capture list with a state word — distilled / distilling / queued, never a glyph.
  • Skills carry provenance. Each produced skill shows its name, the captures it was distilled from, and its install state, inside the #1312 box idiom. /jinn skills show <name> reaches the full source — the claim is checkable, per the legibility principle.
  • Install is a separate, explicit step. Distilling writes skills locally but installs nothing. Install-all, install-one, or skip-and-install-later are all one keystroke or one flag.
  • The reused skill announces itself. In a later run the ◇ skill line (1e) marks the point of use and the model it ran on — the same one-line-at-point-of-use rule as the corpus signal.

Persistence — facts over flags

  • Mode is a real setting in ~/.config/jinn-agent/distil.json — where: local|defer|off, or absent for unset (which triggers first-run consent). Set interactively or by flag; the flag and the prompt write the same value.
  • Install state is a fact, not a flag — a skill is "installed" because it is on the skills path, read the same way /jinn skills reads it. Onboarding-style seen-flags aren't needed; the run derives everything from the captures on disk and the skills written.
  • Resume is derived — --resume distils the first eligible capture with no corresponding skill. A stopped run and a failed run resume identically.

Open questions

  • Binary name. jinn distil (brief) vs jinn-agent distil (used here, matching #1405/#1319). Assumed jinn-agent for shell, /jinn for in-session. Confirm against bin/jinn-layer.ts and the harness-layer CLI conventions.
  • Default distiller. The distiller is the operator's choice (shown in the preview and set with --distiller). The default here is a local frontier-class model, so "nothing leaves the machine" is literally true and cost reads as compute/time. If the common default should instead be a hosted frontier model, the cost line becomes a money estimate and the "what leaves" copy leads with the provider send. Product picks the default; both are drafted.
  • Cost estimate source. ~9 min is a placeholder. The real estimate needs a per-capture token/step count and a local throughput read (or the hosted model's price). Flagged for the implementer.
  • Capture eligibility window. Which traces count — last N, last 7 days, all un-distilled? Shown here as 6 recent captures. Needs a retention/eligibility rule.
  • Re-distillation. Running distil again after new tasks — does it produce new skills, version existing ones, or merge? Assumed: only un-distilled captures are read; a re-run over the same captures is a no-op. Confirm the skill-versioning model.
  • Relationship to #1312 contribution. Distillation consent and corpus-contribution consent are independent toggles — you can distil locally while contributing nothing, or contribute while never distilling. Assumed independent; confirm there's no coupling in the harness settings.
