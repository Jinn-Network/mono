# Implementation plan — issue #117

**Issue:** [#117](https://github.com/Jinn-Network/mono/issues/117) — Wire real RPC and IPFS clients into solver-plugin trust CLI commands
**Design:** `docs/superpowers/specs/2026-05-26-117-design.md`
**Date:** 2026-05-26
**Shape:** `feat` — new CLI verbs; TDD discipline. Skill chain: `writing-plans` → `test-driven-development` → `executing-plans` → `verification-before-completion`.

## Approach summary

Build seven new `jinn solver-plugins` subverbs (`endorse`, `warn`, `block`, `review`, `respond`, `list-feedback`, `discover`, `status`) on top of the existing `solver-plugins.ts` dispatcher and the same `PRODUCTION_DEPS` + `Partial<Deps>` injection shape `publish` / `revoke` already use. Tests mock at the factory boundary; production wires the existing `ReputationRegistryClient`, `createDiscoveryAPI`, `fetchFromIpfs`, `FleetBootstrapper.ensureStage1`, and `createCliSignerContext` building blocks unchanged.

The build is bottom-up: extend `NetworkTrustDeps` and add the production `reputationClientFactory` + `discoveryApiFactory` to `solver-plugins.ts` first (no dispatcher wiring yet), then stack each handler one at a time, each landing with a failing test → implementation → green.

Out of scope (per design §"What stays out of scope"): daemon hot-reload of `blockedCids`, a `jinn trust` top-level group, operator-app dashboard buttons, the Tier-3 Anvil integration test (follow-up issue), and harness-side mirrors (`harnesses endorse / warn / …`).

## TDD order (bottom-up)

1. **T1** Type + dep-factory plumbing in `solver-plugins.ts` (no handlers yet) — purely additive; existing tests stay green.
2. **T2** `endorse` — happy + missing-credential + agentid-unresolvable. (canonical write-verb shape)
3. **T3** `warn` — happy + missing-credential. (mostly mirrors `endorse`; minimal additional coverage)
4. **T4** `review` (+ `respond` via `--response-to`) — happy + happy-respond + missing-credential.
5. **T5** `block` — happy (network + local) + network-fails-but-local-ok + config-write-fails-fatal + missing-credential.
6. **T6** `list-feedback` — happy + agentid-unresolvable + discovery-unavailable.
7. **T7** `discover` — happy + discovery-unavailable + missing-ipfs-config (with `--no-payload` opt-out).
8. **T8** `status` — happy (published) + not-published + discovery-unavailable + works-without-password.
9. **T9** Help-text update + dispatcher invalid-invocation expansion for new verbs.
10. **T10** Verification gate — `yarn typecheck && yarn test` clean.

Each step writes the failing test first, then the production code until green. No step adds more than one handler.

## Tasks

### T1 — `NetworkTrustDeps` + production factories (no dispatcher wiring)

**Files:** `client/src/cli/commands/solver-plugins.ts`, `client/src/config.ts`.

- Extend `SolverPluginsDeps` interface with three new fields:
  ```ts
  reputationClientFactory: (args: {
    reputationRegistryAddress: Address;
    safeAddress: Address;
    rpcUrl: string;
    network: JinnOnchainNetwork;
    earningDir: string;
    password: string | undefined; // undefined → read-only
  }) => Pick<ReputationRegistryClient,
    'giveFeedback' | 'respondToFeedback' | 'revokeFeedback' |
    'readAllFeedback' | 'getSummary' | 'getClients'>;
  discoveryApiFactory: (cfg: ReturnType<typeof defaultLoadConfig>) => DiscoveryAPI;
  ipfsFetch: typeof fetchFromIpfs;
  ```
- Extend `PRODUCTION_DEPS` with implementations. `reputationClientFactory` mirrors the lazy-wallet pattern in `publisherFactory` (lines 94-142): synchronous return, lazy decryption, single shared `ReputationRegistryClient` instance built on first write call. When `args.password === undefined`, construct the client with `walletClient: undefined` so reads work and writes throw the existing `'walletClient required'` error.
- `discoveryApiFactory` calls `createDiscoveryAPI(cfg.discovery ?? { mode: 'onchain' }, { rpcUrl: cfg.rpcUrl, chainId: cfg.network === 'testnet' ? 84532 : 8453 })`. Identity-registry / safe / mech addresses are not required for `listPluginPublications` / `queryEnvelopes` (the only methods the new read handlers call); pass `undefined` for them. Verified by re-reading `discovery/factory.ts` and `discovery/onchain.ts` to confirm those fields are required only for `findClaimableTasks` / `canClaimTask`.
- In `client/src/config.ts`, add `solverPlugins: z.object({ blockedCids: z.array(z.string()).default([]) }).default({ blockedCids: [] })` to `JinnConfigSchema`. The schema default produces `cfg.solverPlugins.blockedCids = []` on every load, so the block handler can append safely without a defensive existence check.

**Acceptance:** `yarn typecheck` passes; `yarn test` still passes (no new tests yet — all existing tests use `Partial<SolverPluginsDeps>` and the additive fields don't affect them). Manually verify by running `yarn typecheck && yarn test` from `client/`.

### T2 — `endorse` handler

**Files:** new `client/src/cli/commands/solver-plugins-feedback.ts`, new `client/test/cli/commands/solver-plugins-feedback.test.ts`. Update `solver-plugins.ts` dispatcher.

**Test first (`solver-plugins-feedback.test.ts`):**

- Happy path: mock `discoveryApiFactory` returns a discovery API whose `listPluginPublications({ })` returns `[{ builderAgentId: '777', cid: 'bafyTestCid', name: '@b/p', version: '0.1.0', supports: ['x.v0'], publishedAt: 1, artifactType: 'plugin', revoked: false, pluginSha256: '0x…' }]`. Mock `bootstrapperFactory().ensureStage1()` returns the stage1 envelope from the publish tests. Mock `reputationClientFactory().giveFeedback` returns `'0xtxendorse'`. Invoke `['endorse', 'bafyTestCid', '--score', '100', '--score-decimals', '2', '--tag1', 'endorsement', '--config', configPath]`. Assert: `giveFeedback` was called once with `harnessAgentId: 777n, score: 100, scoreDecimals: 2, manifestRef: 'plugin:bafyTestCid', tag1: 'endorsement'`, and a 32-byte `manifestHash` equal to `keccak256(toBytes('plugin:bafyTestCid'))`. Envelope on stdout: `{ verb: 'solver-plugins endorse', txHash: '0xtxendorse', pluginCid: 'bafyTestCid', targetAgentId: '777' }`.
- `keystore_missing`: `resolveCliPassword` returns `{ ok: false }`. Assert envelope `{ error: { code: 'keystore_missing' } }`, exit 1, `giveFeedback` not called.
- `agentid_unresolvable`: `listPluginPublications` returns `[]`. Assert envelope `{ error: { code: 'agentid_unresolvable', message: /bafyTestCid/, details: { mode: 'onchain' | 'http' } } }`, exit 1.

**Implementation:**

- Export `endorseHandler(ctx, opts, deps)` from `solver-plugins-feedback.ts`. Pipeline:
  1. `resolveCliPassword` (mirrors publishHandler L51-61).
  2. `loadConfig`.
  3. Build `discoveryApi = deps.discoveryApiFactory(config)`. Call `discoveryApi.listPluginPublications({ })` and find the row whose `cid === opts.pluginCid`. If none, emit `agentid_unresolvable` and exit. Catch `DiscoveryUnavailableError` → emit `discovery_unavailable`.
  4. `bootstrapperFactory(config).ensureStage1(password)` → on `ok=false` emit `ensure_stage1_failed`. Read `fleet_safe_address`, `fleet_agent_id` (for caller identity; used as Safe address on writes).
  5. Compute `reputationRegistryAddress = getReputationRegistryAddress(chainId)`.
  6. `client = reputationClientFactory({ reputationRegistryAddress, safeAddress, rpcUrl, network, earningDir, password })`.
  7. `manifestRef = 'plugin:' + pluginCid`; `manifestHash = keccak256(toBytes(manifestRef))`.
  8. `txHash = await client.giveFeedback({ harnessAgentId: BigInt(builderAgentId), score, scoreDecimals, manifestRef, manifestHash, tag1, tag2 })`. Catch `Self-feedback not allowed` → emit `self_feedback_not_allowed` exit 1. Other throws → emit `publish_failed` exit 1.
  9. Emit envelope, exit 0.
- Update `solver-plugins.ts` dispatcher: add a new branch for `subverb === 'endorse'` that parses `pluginCid` positional, `--score`, `--score-decimals` (default `'2'`), `--tag1` (default `'endorsement'`), `--tag2`, `--config` flags; constructs `EndorseOptions`; calls `endorseHandler(ctx, options, resolvedDeps)`.

**Acceptance:** new tests pass; existing tests stay green.

### T8 — `status` handler

**Files:** `client/src/cli/commands/solver-plugins-read.ts`, `client/test/cli/commands/solver-plugins-read.test.ts`. Update dispatcher.

**Test first:**
- Happy published: discovery returns one row for cid; `reputationClient.getClients(777n)` returns one address; `getSummary` returns `{ count: 3n, summaryValue: 250n, summaryValueDecimals: 2 }`. ## Risks and mitigations

| Risk | Mitigation |
|---|---|
| `listPluginPublications` does not exist on the `OnchainDiscoveryAPI` floor today (only the HTTP backing has full coverage). | Verified in `client/src/discovery/types.ts` — the interface declares `listPluginPublications` as a required method; mainnet's default `mode: 'onchain'` may return `[]` for not-yet-implemented surfaces. Acceptable for #117: testnet uses HTTP by default; mainnet operators get the documented `agentid_unresolvable` until on-chain decoder catches up. Flag as a follow-up if it bites. |
| `solverPlugins.blockedCids` schema addition could break existing config files. | Zod default `[]` plus `solverPlugins` schema `.default({ blockedCids: [] })` means existing config files load unchanged. Verified by re-reading config.ts's preprocessor pattern (lines 465-486 show legacy keys are handled defensively). |
| Read-only `reputationClientFactory` with `password: undefined` is a new code path. | Add a focused unit test for the factory itself in `solver-plugins-read.test.ts` that asserts the returned client's `readAllFeedback` works and `giveFeedback` throws. |
| Tests in `solver-plugins-publish.test.ts` may become stale if `SolverPluginsDeps` grows. | All new fields are optional via `Partial<SolverPluginsDeps>` spread in `createSolverPluginsCommand`; existing tests do not reference the new fields. Verified by re-reading the spread on line 169 of `solver-plugins.ts`. |
