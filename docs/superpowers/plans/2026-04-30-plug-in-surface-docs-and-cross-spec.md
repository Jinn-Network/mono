## Cross-task conventions

- **No new content invention.** Every doc page references concrete artifacts already shipped by earlier plans. The Path 2 SDK reference doc enumerates types from `packages/restorer-sdk/src/index.ts`; the Path 1 manifest reference doc enumerates fields from `client/schemas/jinn-plugin-v1.json`. The walkthrough docs link to their corresponding example packages.
- **One commit per task.** Doc pages are small; each task is roughly one commit.
- **Cross-spec patches go in their own commits.** Five separate one-paragraph edits, separate commits, can land separately if the operator prefers per-spec PRs.
- **Length targets.** Quickstarts ~80–120 lines. Reference docs ~150–250 lines. Walkthroughs ~80–120 lines each. Cross-spec patches ~5–15 lines added per spec.

- [ ] **Step 1.1: Author the doc**

The doc covers, in order:

The doc closes with a "next" link to `slot-reference.md`.

## Task 4: Path 1 compatibility doc

**File:** `client/docs/path-1/compatibility.md`

Versioning + deprecation policy specifically for Path 1.

- [ ] **Step 4.1: Author the doc**

Cover:

1. **claude-code-learner semver discipline.** Major bumps when the slot registration interface, the phase-agent contracts, or the manifest schema break. Minor bumps for additive surface (new slot types, new optional fields). Patch for bug fixes.
2. **Plug-in compatibility ranges.** Plug-ins declare `compatibility.claudeCodeLearner` as a semver range. The loader warns on out-of-range but loads anyway (consistent with Plan 3 Task 4); operators see a fleet-status warning.
3. **Plug-in manifest schema versioning.** `schemaVersion` in `jinn-plugin.json` — Phase A.2 ships `1.0.0`. Future bumps add a new schema file (`jinn-plugin-v2.json`) and the loader accepts both with a 12-week deprecation overlap (matching the SDK).
4. **Slot-type additions vs removals.** New slot types ship as minor bumps of `claude-code-learner`; existing plug-ins keep working. Slot-type removals require major bumps + 12-week deprecation.
5. **Deprecation surface.** Where deprecations are announced (CHANGELOG.md in the daemon repo + the SDK; `console.warn` in the load path; spec discussion thread).

## Task 8: Path 2 publishing

**File:** `client/docs/path-2/publishing.md`

Manifest signing, tarball pinning, IPFS publish, sample CI config.

- [ ] **Step 8.1: Author the doc**

Sections:

1. **Generate an ed25519 signer key.** Sample `node` snippet using `@noble/ed25519`.
2. **Compute the tarball's sha256.** `npm pack --json` + `shasum -a 256`. Include the resulting `package.cid` (IPFS) + `package.hash` (sha256).
3. **Write `jinn.manifest.json`.** Fields populated; `signature` left blank for signing.
4. **Sign the manifest.** Canonicalise (sorted keys, signature stripped — same algorithm as Plan 1 Task 4 step 4.9) and ed25519-sign with the key.
5. **Pin to IPFS.** `ipfs add <tarball>` for the package, `ipfs add jinn.manifest.json` for the manifest.
6. **Publish the npm tarball** alongside (the daemon resolves the *package* from npm + the *manifest* from IPFS).
7. **Sample CI** — a GitHub Actions workflow that runs unit + e2e tests, builds, computes the hash, signs the manifest, and emits the manifest CID as a release artifact.
8. **Operator-side install** — `jinn impls trust ed25519:<base64-pubkey>` then `jinn impls add ipfs://<manifest-cid>`.

Cross-references `spec/2026-05-executor-trust-boundary.md` §5 for the canonical signing + trust spec.
