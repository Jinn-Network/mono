# DR-2026-09-06 — The native anchor target is declared, not fixed; anchor digests commit to their act

## Context

Two questions were left open when the native identity ceremony shipped, and PR #2511 surfaced both as findings.

The first: what address may an anchor transaction be sent to? §3.2 asserted a "fixed anchor target", and nothing in the tree fixes one. The only anchor-target constant anywhere is the e2e fixture's own test value (`operator/test/e2e/fixtures/native-fleet/anchor.ts:24`); the production path takes a `--anchor-target` flag (`operator/src/cli/commands/ceremony.ts:73`) that defaults to the operator's own agent EOA (`:644`). The spec asserted a constraint that was never built.

The second: what is an anchor digest a digest of? The catalog schema constrains nothing about the digest's meaning. The reader checks the exact declared bytes at the declared offset (`operator/src/daemon/native-base-sepolia-infrastructure.ts:1468-1471`) and nothing else, and the catalog opener checks only referential integrity — every binding and every revocation declares at least one anchor, and every referenced digest appears in `anchors[]` (`operator/src/daemon/native-trust-catalog.ts:326-343`). No relation between an anchor's digest and the content of the records referencing it is checked anywhere.

The implementation answered the second question for genesis and join without the spec saying so: `ceremonyAnchorDigest` (`operator/src/cli/commands/ceremony.ts:412-428`) hashes the session tuple `{protocol, agent, admissionAgent?, settlementSafe, keys}`. It answered nothing for revocation, because `revokeBinding`'s body is deferred (ceremony spec §3.2, §9) — while `RevocationSchema` already requires `anchors` (`packages/trust/core/src/revocation.ts:27`) and the opener already refuses a revocation with none (`native-trust-catalog.ts:336`). The first revocation ever authored would have had to invent its digest content on the spot.

One structural fact frames both answers: **the anchor digest can never be the sealed record's own digest.** `KeyBinding.anchors` is a required field of the record (`packages/trust/core/src/key-binding.ts:73`), and `Revocation.anchors` likewise, so a record that must contain its anchor's digest cannot be that digest's preimage. The binding case is doubly forced, because §6 law 2 requires `validFrom` to be the anchor's block time verbatim, which is unknowable before the anchor mines. §7.3 of the trust-layer design says "The binding's digest receives a time anchor" (`2026-07-27-trust-and-identity-layer-design.md:290`); the implementation cannot do that, and the reason is circularity, not laziness.

## Decision

The clauses below are split by where they belong. **Protocol** clauses cross in substance to the anchor-locator profile document — `https://spec.jinn.network/trust/anchor-locators/base-sepolia-calldata-v1` is a `spec.jinn.network` identifier, so that document is protocol and is authored in `Jinn-Network/spec` under DR-2026-09-03; it does not yet exist in any repository. **Mono-side operational** clauses are this repository's defaults and do not cross.

**1. Protocol — the anchor target is declared, not constrained.** No protocol-wide anchor-target constant exists, and none is created. `contractAddress` is a consistency field: it forces the locator's author to declare the recipient and fails the read closed on mismatch (`native-base-sepolia-infrastructure.ts:1460`). It is not evidence. A finalized Base Sepolia transaction supplies all three properties an anchor surface owes — append-only writes, tamper-evidence, consistent observable order (`2026-07-27-trust-and-identity-layer-design.md:290-295`) — from the block, not from the recipient.

A fixed constant would cost three things. It re-introduces the liveness coupling rule 4 forbids (`:197-199`), because a shared address that holds code makes an anchor transaction hit its fallback, a contract without an accepting fallback reverts, and the reader requires `receipt.status === 'success'` (`native-base-sepolia-infrastructure.ts:1458`) — "can anyone create a native identity?" becomes a function of that address's current code. It makes anchor validity mutable after the fact, because any constraint over chain state at the target can flip (`CREATE2`), which silently un-verifies catalogs that booted yesterday — the defect §2.3d already rejects for ERC-1271 ceremonies. And it buys nothing measurable: no `from` check exists, so it adds no attributability, and enumerability by scanning one address is something the catalog already provides by naming the transaction hash outright.

**2. Protocol — `ceremony-anchor/v1` is ratified as authored, with its canonicalization pinned.** ECMA-262 `JSON.stringify`, no replacer and no `space`, keys inserted in the order `protocol`, `agent`, `admissionAgent` (**omitted entirely** when absent, never `null`), `settlementSafe` (ASCII-lowercased), `keys` (objects of exactly `role` then `keyId`, sorted ascending by `role` under JavaScript string comparison — UTF-16 code-unit order); UTF-8 encoded, sha256, spelled `sha256:<64 lowercase hex>` (`operator/src/cli/commands/ceremony.ts:412-428`, `packages/trust/core/src/hashing.ts:10-12`). Every preimage value MUST be ASCII: `JSON.stringify`'s escaping is minimal and unambiguous for ASCII and raises lone-surrogate questions otherwise. Non-ASCII is out of profile for v1 and MUST be refused at authoring time; nothing checks it yet, which is why §Consequences carries the guard as work this record authorizes.

Ratified rather than replaced because the preimage is a deterministic function of the session tuple, which is what makes `reusableAnchor` (`operator/src/cli/commands/ceremony.ts:333-349`) a correct crash-resume, and because replacing it would cost every existing deployment a re-anchor to buy nothing that is checked today.

**3. Protocol — the defect that preimage carries is recorded, not fixed here.** It is **not *directly* third-party recomputable**. Three of its five terms are read straight off any catalog — `protocol` is a literal, `agent` and `admissionAgent` are binding `agent` fields (`ceremony.ts:719-721`), and each `keyId` is `key.didKey` verbatim (`key-binding.ts:58-63`). A fourth, `settlementSafe`, is read off a settlement-scoped binding's ceremony evidence, which the catalog entry carries beside the envelope (`native-trust-catalog.ts:183`, third resource at `:257`, `:553-560`) — but **only if the catalog has such a binding**. The Safe is written under the `isSettlementRole` guard alone (`ceremony.ts:744`) and stored nowhere else, so a settlement-free provisioning such as `--role-sets requester` (`native-requester.ts:46-51`) carries no Safe at all. The fifth term is in no catalog: `KeyBinding` carries no `role` field (`:55-74`) and the §3.2a role → scope map is not invertible — the three `*-discovery` roles share one scope pair and both settlement roles map to `settlements` — so the `role` labels cannot be read off.

For a catalog that has a settlement binding, that confines the ambiguity to an ordered selection from each collision class: `P(3, d) × P(2, s)` candidates for `d` discovery and `s` settlement bindings — and because `--role-sets` must always include `requester` (`ceremony.ts:250-258`), that is **exactly `3! × 2! = 12` for every provisionable shape carrying a settlement binding**, partial ones included (`requester,solver` gives `P(3,2) × P(2,1) = 12`). The smaller products belong only to the settlement-free shapes, for which the check is unconstructible anyway. The count assumes a third party working from scopes alone; one who also assumes CLI-authored role sets does better on partial shapes, and twelve stands as the honest upper bound. A third party enumerates them, hashes each, and either matches the anchor digest — opening the commitment and learning the assignment — or refuses. So the commitment is **not** inert there, and a check against `ceremony-anchor/v1` as authored is implementable today at twelve sha256 calls and no re-anchor. What it lacks is a direct recomputation. For a settlement-free catalog the check is unconstructible rather than imprecise, the missing term being a 160-bit address; that shape has no check short of the successor preimage. The corrective is a directly recomputable preimage; it changes the preimage and therefore costs every deployment a re-anchor, while the enumerating check buys most of its evidentiary value at none of that cost. It belongs to the anchor-locator profile document, and changing the preimage twice is worse than once.

**4. Protocol — `revocation-anchor/v1`, recomputable by design; and the rebind keeps `ceremony-anchor/v1`.** The rotation path is two acts and takes two anchors, **both freshly submitted**: the revocation's is the new preimage below, and the rebind's is `ceremony-anchor/v1` over exactly the replacement bindings that act authors (ceremony spec §3.2b), which is what that preimage's own contract already means by "the key set this ceremony session is about to bind". The rebind anchor is fresh by rule and not merely by law 1's permission, because the narrow preimage makes a cross-act digest collision reachable — a prior act that anchored exactly this replacement key set — a repeated rebind, or a wholesale rebind back to a previously anchored set — recomputes an already-mined digest (the preimage commits to the whole `keys` set, so re-binding one pair that was anchored inside a larger set does not collide) — and reusing it would hand the rebind an older block time as `validFrom`, which is binding-side retroactivity of the kind R2 forbids for revocations. A new preimage over `{protocol, targets[], revokedBy}`: the literal `https://spec.jinn.network/trust/revocation-anchor/v1`; the revoked binding digests, each `sha256:<lowercase hex>`, sorted ascending as strings, no duplicates, at least one; and the revoking identity exactly as it appears in the records. Same encoding discipline as clause 2. `effectiveFrom` is deliberately excluded — including it would force it to be chosen before the anchor exists and would then be a published commitment to a value the resolver clamps away (`packages/trust/resolve/src/binding-resolver.ts:147`).

Rules R1–R5, ratified as §6 law 6 of the ceremony spec: **R1** exactly one anchor per revocation, newly submitted for that act; **R2** no cross-act reuse ever, because the resolver takes the earliest anchor time (`binding-resolver.ts:111-116`) and a revocation's effect is `max(effectiveFrom, earliest anchor time)` (`:147`), so referencing a binding's anchor revokes it from the moment it existed — a direct violation of "revocation is never retroactive" (`2026-07-27-trust-and-identity-layer-design.md:330-332`); **R3** one anchor MAY back several revocations exactly when they share `revokedBy` and their `target` set is exactly the preimage's `targets`; **R4** `effectiveFrom` is millisecond-ISO UTC at or before the anchor's block time, the millisecond form required because `:147` compares raw strings lexicographically; **R5** anchor first, for law 1's reason.

Every term is present in the catalog, so a verifier can recompute the digest and refuse a mismatch. That collapses R1–R3 into one check and makes R2 structurally unfalsifiable rather than merely forbidden: domain separation means a `revocation-anchor/v1` digest can never equal a `ceremony-anchor/v1` digest. Because `effectiveFrom` is deliberately outside the preimage, two distinct acts sharing `targets` and `revokedBy` recompute the same digest and the check cannot tell them apart — which is exactly R3's sanctioned equivalence class, the one where reuse changes nothing, since the earlier act already took effect at that time. One corner for whoever implements R3: a `did:key` revoker's authorization is resolved *at* the revocation's effective time (`packages/trust/core/src/verify.ts:265-271`), so an anchor predating the revoker key's own binding makes the revocation silently no-op.

**5. Protocol — exactly one anchor per record.** Under this profile a binding and a revocation each declare exactly one anchor. Everything Jinn authors already writes a single-element array (`packages/trust/authoring/src/binding.ts:112`), so this invalidates nothing; it closes an earliest-wins ambiguity that has no legitimate use here and that R2 shows is dangerous.

**6. Protocol — the enforcement split is published with the rules, and the residual has exactly one bound.** §3.2b states, rule by rule, which clauses the verifier checks today and which are authoring convention it is blind to, and states the residual honestly: because the digest's meaning is unchecked, an anchor's timestamp can be borrowed from any pre-existing Base Sepolia transaction, and earlier-anchored wins conflicts. One thing is genuinely bounded — it is a borrowed timestamp and not a forged binding, since the DSSE self-signature and the EIP-191 ceremony are untouched, and grinding a digest to match an existing transaction is a preimage problem. **The other two bounds an earlier draft of this record claimed do not hold, and §3.2b now says so.** The §7.4a consent chain does *not* block foreign-IRI attachment regardless of anchor time: its first exit is genesis (`packages/trust/core/src/verify.ts:201`), and genesis is decided by earliest `effectiveStart` among every binding asserted for the IRI (`binding-resolver.ts:217-223`, `:298`), so a borrowed pre-genesis anchor is the lever that opens the exemption rather than something it survives. The residual also runs in the revocation direction, where it is sharper: a borrowed pre-evidence anchor makes a revocation retroactive against §7.4b, and because the resolver fetches revocations for the winning binding's digest alone (`binding-resolver.ts:279`), an earlier-anchored replacement binding escapes revocations bound to the record it supersedes. R2 forbids reuse; neither of these is reuse. What contains all of it is catalog write authority — a record must reach the verifier's catalog to resolve, and joins are serialized through whoever holds that file — which is procedural, not cryptographic, and is the residual's real and only boundary. This corrects the statement of the residual, not a decision: clauses 1–5 and 7–10 stand as ratified, and the genesis-determination question travels with the recomputation work at §10 (f). A specification that does not say which of its rules are checked is how §3.2a's class of drift happens — and one that overstates its bounds is the same failure wearing a reassuring face.

**7. Mono-side operational — the self-send default and the flag stay.** `--anchor-target` keeps its 20-byte hex validation (`operator/src/cli/commands/ceremony.ts:619-622`) and its default of the operator's own agent EOA (`:644`); the justification recorded inline at `:640-643` is now the ratified reason rather than an implementation choice. It is an override of a default, not an escape from a rule.

**8. Mono-side operational — the re-author choice is stated, not fixed.** Because the preimage is a pure function of the session tuple and the re-author runbook touches no key, store, or Agent IRI, a re-author recomputes the identical digest, so the anchor MAY be reused. It is not automatically correct, and — contrary to what the runbook said before this change — reuse is also what the CLI does by default. `init` refuses while the catalog exists (`ceremony.ts:949-966`) and there is no `--force`, so the re-author has no supported path today; the only way past that guard leaves the run receipt at `<dir>/ceremony/receipt.json` (`:266-270`), where `reusableAnchor` (`:333-349`) matches the recomputed digest and resumes onto the already-mined anchor (`:1002`). Minting fresh requires moving the receipt aside as well. Reuse preserves the original `validFrom` and effective window, claiming the widened scope retroactively over evidence signed before the widening; a fresh anchor refuses that retroactivity at the cost of a coverage gap. The runbook MUST state the choice, including which act selects it, and the operator MUST record the reason.

**9. Carried forward as requirements on the anchor-locator profile document.** Two corrections are owed to it and are recorded here so its first published version is right rather than compatible with a mistake. First, **the field is named `to`, not `contractAddress`**: no contract need exist at the target, contract-creation transactions are structurally refused (`sameHex` rejects a `null` left operand, `native-base-sepolia-infrastructure.ts:681-683`; `to` is nullable by the port's own type, `:574`), and the field holds a plain recipient. The wire key nonetheless stays frozen at `contractAddress` for `base-sepolia-calldata-v1` — a `z.literal`-pinned profile (`native-trust-catalog.ts:60-70`) with a live operator-held catalog behind it, where renaming a field is exactly the "new profile, not a parameter" change §3.3 governs. Second, **the successor binding-anchor question travels with it**: whether to replace `ceremony-anchor/v1` with a *directly* recomputable preimage, on what trigger, and what to do about the settlement-free shape the enumerating check of clause 3 cannot reach. It is carried as a question, not a mandate — clause 3 ratifies the current preimage and §Deliberately left open defers the corrective to [#4172](https://github.com/Jinn-Network/mono/issues/4172), so this record must not also require it.

**10. Not retroactive.** No existing artifact is invalidated. See §Consequences.

## Alternatives considered and rejected

- **A single fixed protocol-wide anchor-target constant.** Rejected on all three costs in decision 1. The strongest form — an inert burn address nobody controls — dissolves the liveness and mutability costs and still buys nothing, which is the whole of its case.
- **"The target MUST be an address the ceremony signer controls."** Rejected as unverifiable. Control of an EOA is demonstrable only by a signature, and no signature over the target exists; it would be an unenforceable rule dressed as a check, which is the thing decision 6 refuses to do. It survives as the *default* (decision 7), which is the honest form of the same intent.
- **"The target MUST have no contract code."** Rejected on retroactive mutability: an address with no code today can hold code tomorrow, so an already-mined anchor's validity would flip. The receipt-success check already excludes the failure this aims at.
- **"`contractAddress` MUST equal `transaction.from`" — a real self-send check.** The only constraint in the family a verifier could actually enforce, since `from` is available, so it is named rather than passed over. Rejected anyway: it couples anchor gas to the ceremony key and forbids a coordinator or relayer paying it, which is a liveness coupling in miniature; and it buys nothing, because an adversary who anchors someone else's digest hands them a valid *earlier* timestamp they cannot exploit — they still cannot produce the binding.
- **Renaming the wire key `contractAddress` → `to` now.** Rejected: it is a profile change under §3.3's own rule, against a live operator-held catalog, for a cosmetic gain. Deferred to the profile document (decision 9).
- **Replacing `ceremony-anchor/v1` with a directly recomputable preimage in this ratification.** Rejected: it costs every existing deployment a re-anchor, and it is not the only way to get a third-party check — the enumerating check of decision 3 works against every anchor already mined, at no deployment cost, so the replacement buys precision rather than openability. The check belongs to the profile document, and changing the preimage once there is better than changing it twice (decision 3).
- **Committing `effectiveFrom` inside the revocation preimage.** Rejected: it would have to be chosen before the anchor exists and would be a published commitment to a value the resolver clamps away — a field that looks authoritative and is not.
- **Leaving revocation digest content unspecified until `revokeBinding` ships.** Rejected: the schema and the opener already require the anchor, so the first implementer would invent the content under time pressure and every subsequent revocation would inherit it. It is free to fix while zero revocations exist and expensive afterwards.

## Consequences

**Nothing is invalidated, and no verifier check is added by the ratification itself.** Every anchor, binding, revocation, and catalog that verifies today verifies unchanged afterward, byte for byte — including the operator-held DR-2026-08-05 gate catalog, which is not in this repository. The only way a ratification of this shape could invalidate an artifact is by adding a check, and the one check it recommends applies exclusively to revocation anchors, of which none exist because `revokeBinding`'s body was never implemented. That is why this is the right moment: the binding paths are frozen at zero cost and the revocation path is fixed before its first artifact.

**Work this authorizes**, each citing ceremony spec §3.2b and §6 law 6 and this record, so that no implementation converts a choice into protocol a second time:

- The **rotation follow-up** deferred by ceremony spec §9 (`revokeBinding` + rebind + `jinn ceremony rotate`) is unblocked in both halves. Its revocation half was blocked on the undefined digest content decision 4 supplies; its rebind half authors a replacement binding under a new anchor, and §3.2b now names that anchor's digest too — `ceremony-anchor/v1` over the replacement keys alone, two acts taking two anchors. Naming only the revocation half would have left the rotation implementer inventing the other one, which is the failure this record exists to prevent.
- A **revocation act-binding check** in `openNativeTrustCatalog`: recompute `revocation-anchor/v1` from the referencing revocations and refuse a mismatch. Small, self-contained, and it subsumes R1–R3.
- An **exactly-one-anchor guard** in the catalog opener, per decision 5.
- An **ASCII refusal at authoring time**, per the encoding discipline in clause 2. Every
  preimage value is ASCII today (`urn:uuid:` IRIs, base58 did:keys, hex addresses), so this
  guards the invariant rather than fixing a violation. It is listed here because the rule is
  new and nothing checks it, and an unchecked rule with no owner is how §3.2a drifted.
- The **one-word spec correction** (§3.2's "fixed" → "declared"), applied in the same change that carries this record.
- The **runbook section** in `docs/runbooks/native-trust-reauthor.md` stating the reuse-vs-fresh choice, its two costs, and the requirement to record the reason, per decision 8 — applied in the same change that carries this record, because §3.2b states the requirement as a MUST on that runbook and shipping an already-violated MUST with no owner is the drift this record exists to refuse.

**Work this invalidates: none in flight.** Any implementation that had begun defaulting `--anchor-target` toward a shared constant would be overturned, and none has — no such production constant exists in the tree.

**PR #2511's two findings.** Finding 1 (no anchor-target constant) resolves as **not a gap**: the absence was correct, and the choice made there by default is now the ratified reason. Finding 2 (digest content underdefined) resolves as **the real gap, and larger than reported** — not merely that revocation was unspecified, but that the specified binding preimage is not directly recomputable by a third party, openable only by enumerating the role permutations the scope map cannot distinguish.

**Deliberately left open**, recorded as ceremony spec §10 (e) and (f) rather than settled here: whether the re-author path should reuse its anchor or mint a fresh one, which is a retroactive-authority policy question exceeding an anchor-format ratification; and whether a successor binding-anchor preimage should be *directly* third-party recomputable and on what schedule the re-anchor it implies is worth paying, given that the enumerating check described in decision 3 is available today without one. Both are owned by [#4172](https://github.com/Jinn-Network/mono/issues/4172), filed with the ruling so that the defect decision 3 ratifies has a holder and a trigger rather than only a paragraph. Their destination is still the anchor-locator profile document under DR-2026-09-03; the issue is what carries them there.
