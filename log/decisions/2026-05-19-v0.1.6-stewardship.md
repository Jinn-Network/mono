## v0.1.7 release-blockers — bugs surfaced by this session

### Bug #1 — Hermes provider routing ignores OpenRouter-format model id

**Symptom:** Op B joined with `model: "deepseek/deepseek-v4-flash"` (the canonical HERMES_MODELS id format `<provider>/<model>`). Hermes child process called `cloudcode-pa.googleapis.com` (Google Code Assist) anyway and died with `HTTP 404: Code Assist 404`. Hermes was using its operator config.yaml's default `provider: google-gemini-cli` and ignoring the model id's implicit OpenRouter routing.

**Root cause:** `client/src/harnesses/impls/hermes-agent/adapter.ts:138` only passes `--provider` to the Hermes child if `config.hermesProvider` is non-empty. The daemon's adapter construction site (in `main.ts`) does not derive provider from the model id format. The join form does not surface a provider field. Hermes downstream defaults to the operator's pinned provider in `$HERMES_HOME/config.yaml`.

**Fix shape:** When the model id matches `/^[a-z0-9_-]+\/[a-z0-9_.-]+$/`, the daemon should pass `--provider openrouter` to Hermes. Either compute it in `main.ts` when constructing `HermesHarnessAdapter`, or in `HermesHarness.runTask` before launching the child. One-line additional inference, no schema changes.

**This session's workaround:** rewrote `/tmp/jinn-op-b-2026-05-19/.hermes/config.yaml::model.provider = openrouter`. Confirmed Hermes then routes correctly to OpenRouter and DeepSeek responds (10+ API calls before Bug #2 took over).

**Impact if unfixed:** every Hermes operator picking any HERMES_MODELS entry today gets the same Google-default routing and dies. The canonical model list shipped in #292 is essentially non-functional without Bug #1's fix. This is a v0.1.7 release-blocker.

### Bug #2 — jinn-client MCP plugin can't find the daemon's server entry in dev-layout installs

**Symptom:** Hermes runs the LLM loop, executes tools (terminal, todo, skill_view), but `submit_typed_payload` and `get_task` are unreachable because the `jinn-client` MCP server fails 3 startup attempts. Without it, Hermes cannot submit a solution envelope, the task times out before delivery, the verdict path is starved.

**Root cause:** `client/plugins/network-tools/mcp/jinn-client-server.mjs` (the per-plugin MCP launcher) resolves the daemon's server entry by walking `<pluginRoot>/../../{dist/mcp/server.js,src/mcp/server.ts}`. When the daemon spawns the plugin from a TASK working directory (per the per-task `solver-plugins/` copy under `$HOME/.jinn-client/solver-plugins/network-tools/`), the `../..` walk lands at `$HOME/.jinn-client/` — which has no `dist/mcp/server.js`. The launcher throws "Unable to find the Jinn client MCP server" and the connection retries 3× before giving up.

**Fix shape:** The daemon must inject `JINN_NETWORK_TOOLS_CLIENT_ROOT=<client-install>` (or `JINN_NETWORK_TOOLS_MCP_SERVER_PATH`) into the env block passed to Hermes's mcp_servers config. The wiring point is `client/src/harnesses/impls/hermes-agent/config-builder.ts:120` (`env: { ...jinnEnv, ...(server.env ?? {}) }`) — `jinnEnv` should include the client root resolved from `process.execPath`'s containing dist tree. Alternatively, the plugin's launcher can derive the client root from `process.execPath` when other lookups fail. Either fix is small and well-contained.

**Verification path after fix:** restart Op B, observe `[harness-engine] tick: process(<request>) succeeded` in the daemon log, capture envelope CID + delivery tx + non-trivial verdict score.

**Impact if unfixed:** Hermes harness is effectively unusable in any non-package-layout install (which is the typical development setup AND the post-fleet-bootstrap layout where per-task plugins live under `$HOME/.jinn-client/solver-plugins/`). This is the harder of the two release-blockers because the plugin's `pluginRoot` correctly cannot be at the client install in a per-task copy — the fix has to come from the daemon's env injection.
