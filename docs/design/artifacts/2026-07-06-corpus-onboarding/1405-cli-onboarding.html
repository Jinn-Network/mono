Persistence model — facts over flags

State lives in ~/.config/jinn-agent/onboarding.json, but wherever a step corresponds to a real-world fact, the fact wins: consent is read from the consent record (#1312's store), step 2 from the ledger being non-empty. Only steps 3 and 4 need pure seen-flags. Consequences:

  • Returning operators see nothing. Consent recorded + ledger non-empty derives every gate as satisfied — launch is identical to any other (the returning op state in 1a). Non-destructive by construction: onboarding never writes to the consent record or the ledger, it only reads them.
  • Deleting the flag file re-runs only steps 3–4. Consent and publish state survive because they were never onboarding's to keep.
  • jinn-agent onboarding --replay re-renders all four screens but re-asks nothing — a recorded consent shows its current state with a pointer to jinn-agent contribute, and the publish step shows the actual first envelope from the ledger.

One confirmed step at a time

  • Every screen exits on an explicit key — Enter, A/D, Y/N, S. Nothing auto-advances on a timer; step 2 advances on a real event (the publish) and says so.
  • Step 2's waiting screen renders once and gets out of the way — onboarding must not hold the terminal hostage while the operator works. The publish confirmation appears when the event fires.
  • The step rail (consent · publish · rewards · signals) is words, not glyphs — colour carries state (green done, gold current, amber skipped, dim future), per the no-unicode-icons rule.

Voice — where the metaphor drops

Consent and money screens are plain speech end to end (protocol non-negotiable): "capture is off until granted", "publication alone does not pay", "verification triggers it, and it is not guaranteed". Vow-language appears only in neutral chrome — the scrying, the ether rule on the splash. The OLAS step deliberately names the tier ladder (tests-passed → evaluator-verified) with the same colours the ledger (#1312) and the explorer (#1406) use, so the operator meets one tier system everywhere.

The seam with the explorer

Step 2's gold deep link — explorer.jinn.network/corpus/bafkreid6qv…shxv4 — lands on the #1406 corpus-item detail: same task summary, tier, envelope ref, and anchor tx, field for field. The CLI states what was published; the explorer proves it. Same envelope previewed in #1312's consent preview.

Open questions

  • Splash → onboarding hand-off. Shown as the #1319 splash rendering first with a first run divider replacing the ether, then step 1. If the harness needs the splash and consent on one screen for very short terminals, the banner compresses to the wordmark rows only — flag for the terminal-capability probe.
  • Step 2 on evaluator-less nets. If the operator's first task runs on a SolverNet with no evaluators, evaluator-verified is unreachable; the rewards copy should then say so explicitly. Needs a per-net capability read.
  • Signal-line density cap. A run using many corpus skills could emit many ◇ corpus lines. Assumed acceptable (one per use is the honest record); if noisy in practice, collapse repeats per skill per run. Implementer's call.
