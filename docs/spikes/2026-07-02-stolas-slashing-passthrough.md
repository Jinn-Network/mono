# Spike finding — stOLAS slashing pass-through + co-bond support

- **Issue:** #1316 (`spike`)
- **Date:** 2026-07-02
- **Author:** Jinn contributor
- **Status:** finding — escalates `needs-decision`. Spike code does not merge; this document is the deliverable.
- **Blocks:** v0.5 earning mechanics (`spec/2026-07-02-jinn-harness-network.md` §6.1 Tier 2/3, §12), not v0.

## TL;DR

1. **There is no slash pass-through to the stOLAS pool because, by construction, there is no slash.** The only party authorised to slash a service's bond is that service's own multisig (`ServiceRegistryTokenUtility.slash`, [upstream L553–612](https://github.com/valory-xyz/autonolas-registries/blob/main/contracts/ServiceRegistryTokenUtility.sol)), and every distributor-created multisig carries a `MultisigGuard` that reverts any transaction leaving the pool's bond below the security deposit (`contracts/src/vendor/stolas/MultisigGuard.sol:193-194`) — including the slash transaction itself. The guard is live on the Base-mainnet distributor (read 2026-07-02: `guard() = 0x4D3911420a8E4E7dB8c979f4915dA8983C5e3ba2`, wired to SRTU `0x34C895f302D0b5cf52ec0Edd3945321EB0f83dd5`).
2. **The only native penalty is eviction — forfeited future rewards, never principal.** OLAS staking (`StakingBase.sol`) accrues inactivity and evicts (`checkpoint` → `_evict`, vendored L1038–1063, L488); the bond and deposit sit in `ServiceRegistryTokenUtility`, untouched.
3. **An operator co-bond slice is NOT natively supported by the distributor.** `ExternalStakingDistributor.stake()` always lends the full `minStakingDeposit × 2` from the pool with `NUM_AGENT_INSTANCES = 1` hard-coded and no operator-deposit parameter (`contracts/src/vendor/stolas/ExternalStakingDistributor.sol:208-212, 654-672`). The reward split is per staking proxy, not per operator (`setStakingProxyConfigs`, L842–886).
4. **Tier-3(a) needs a wrapper — and the wrapper is more than plumbing**, because it must introduce the slashing authority that the OLAS stack deliberately lacks (see §Spec flags).

## (a) Slash → pool transmission mechanics

Three layers, read from the vendored source (which diff-matches upstream [LemonTreeTechnologies/olas-lst](https://github.com/LemonTreeTechnologies/olas-lst) — the canonical stOLAS repo, linked from [lstolas.xyz](https://www.lstolas.xyz/); `valory-xyz/olas-lst` does not exist — @ `019b21e` up to import paths and the refactors listed in its `MODIFIED_CONTRACTS.md`):

- **Staking layer — no principal at risk.** The staking proxy holds only reward funds. Missed liveness accrues `inactivity`; past `maxInactivityDuration` the service is evicted (`contracts/src/vendor/registries/staking/StakingBase.sol:1038-1063`). Eviction ends reward accrual. `unstake` returns the service NFT and pays accrued reward; principal never transits the staking contract.
- **Registry layer — the only slash that exists.** `ServiceRegistryTokenUtility.slash(agentInstances, amounts, serviceId)` requires `msg.sender == multisig` of that same service, reduces the named operator's bonded balance, and accrues the slashed amount to `mapSlashedFunds[token]` (drainable by the registry owner — the OLAS DAO, not the pool). `unbondTokenRefund` then returns the *post-slash* balance ("the zero refund scenario is possible if the operator was slashed" — upstream L508–543).
- **If a shortfall ever reached the pool, it would be silent, not priced.** On unstake the distributor decrements its `stakedBalance` bookkeeping by the full deposit regardless of what actually comes back (`ExternalStakingDistributor.sol:730`), so a shortfall lands in its OLAS balance, socialised across the pool. On L1, `stOLAS.totalAssets()` is the sum of *bookkept* balances (`contracts/src/vendor/stolas/l1/stOLAS.sol:326-340, 365-367`); there is **no mark-down function** — `topUpRetiredBalance` (L290–319) only decrements by amounts actually received, so a loss persists as phantom `stakedBalance`: the exchange rate never drops, and the loss falls on the *last* redeemers (upstream `Treasury.finalizeWithdrawRequests` pays from whatever OLAS actually arrived — final withdrawers' transfers revert), rather than being socialised pro-rata. The stOLAS whitepaper is silent on the slash scenario.
- **But the guard closes the path.** `MultisigGuard.checkAfterExecution` runs after every multisig transaction and reverts unless the distributor-as-operator's bonded balance still equals the security deposit (`MultisigGuard.sol:170-195`). Since slash can only be called *by* that multisig, the slash reverts atomically. The guard is structurally required — `stake()` unconditionally sets it during Safe creation (`ExternalStakingDistributor.sol:364-378`) — and is set on mainnet (chain read above; distributor proxy `0x40abf47B926181148000DbCC7c8DE76A3a61a66f`, impl `0xDAE0B11e5bF81216283cB95d30039fA3D650eFE3`, ~110k OLAS currently lent).

Net: **pool principal is currently protected against slashing entirely; the pool's real exposure is eviction churn (lost yield), not loss of stake.**

## (b) Native co-bond support: NO (distributor) / YES-in-principle (registry)

- The distributor cannot express a mixed bond: full deposit always pool-lent, one agent instance, one operator (itself), fixed per-proxy reward factors (collector/protocol/curating-agent summing to 100% — mainnet decodes 5/10/85). The operator is only the recorded `curatingAgent` (`ExternalStakingDistributor.sol:675`). Jinn's client mirrors this as a binary `staking_mode: 'standard' | 'self-bond'` (`client/src/earning/types.ts:4-6`) — all-pool or all-own, nothing between.
- The *underlying* `ServiceRegistry` natively supports multiple operators each bonding distinct agent instances of one service, with per-operator balances and per-operator slash targeting (`registerAgents`, upstream L389–470; `slash` resolves `mapAgentInstanceOperators` per instance). But two caveats keep this short of a native tranche: granularity is one whole instance-bond, not an arbitrary slice; and there is **no priority ordering** — `slash` hits whichever instances the multisig names, so "operator slashes first" would be multisig policy, not contract-enforced. And it is unreachable through the distributor anyway (service creation fixed at one instance); worse, the `MultisigGuard` invariant `operatorBalance == securityDeposit` would brick any service whose bond was partially topped up or partially slashed.

## (c) Does Tier-3(a) need a thin wrapper? YES — and it carries new mechanism

A fork/extension of `ExternalStakingDistributor` (Jinn already vendors it and deploys its own on testnet — `contracts/deployment-stolas-l2-baseSepolia-fast.json`) would need to: accept an operator co-deposit; register the operator (or a wrapper holding its slice) as a second bonded party or track the slice internally; make the curating-agent reward factor a function of the co-deposit. That part is thin. What is **not** thin: (1) nothing in the OLAS stack ever *triggers* a slash for bad work — slashing is a capability the service's own multisig must invoke, and the guard currently forbids even that. "Co-bond slashes first" therefore requires Jinn to define the slashing authority and conditions (who may slash the junior slice, on what evidence) — a new trust surface, not plumbing. (2) The `MultisigGuard` invariant must be redesigned for co-bonded services, since it hard-requires the operator balance to equal the full security deposit. On mainnet the canonical distributor is owner-configured upstream; Jinn cannot reconfigure it and would deploy its own variant alongside.

## Spec flags — assumptions this finding contradicts

- **§6.1 Tier 2 "loosen with slash data":** there is no native slash data to collect. The native penalty signal is *eviction*, and pool principal is guard-protected by design. The knob survives, but its data source must be redefined as eviction/liveness history (or a Jinn-defined slash once Tier-3(a) exists).
- **§6.1 Tier-3(a) "slashes first":** has no native substrate. The spec's hedge in §12 ("supported natively or needs a thin wrapper") resolves to **needs a wrapper**, and the wrapper must introduce the slashing mechanism itself — scope it as mechanism design, not integration.
- Upside for the Tier-2 safety story: "the stOLAS pool prices and socialises that risk" overstates today's risk — depositor principal is currently not slashable at all; the pool's cost of bonding a bad operator is forgone yield on an evicted slot.
