# Design — Wire real RPC and IPFS clients into solver-plugin trust CLI commands (#117)

**Status:** design — Stage 1 output of the headless implement-issue flow for [Jinn-Network/mono#117](https://github.com/Jinn-Network/mono/issues/117).
**Author:** Stage 1 design subagent
**Date:** 2026-05-26

## Problem framing

The issue body claims that "the solver-plugin / harness network-trust CLI surfaces parse commands and local configuration correctly, but some publish/read paths are still wired through stub clients instead of real RPC and IPFS clients," and lists the verbs *endorse / warning / block / review / list-feedback / discover-plugins / status* as the affected surface.

A read of the worktree shows the network-trust CLI surface is **not yet implemented at all**, not "wired to stubs":

- `client/src/cli/commands/solver-plugins.ts` exposes only `show | validate | pack | publish | revoke`. `publish` and `revoke` are already fully wired to real RPC + IPFS via `PRODUCTION_DEPS` (`bootstrapperFactory`, `pinFileToIpfs`, `publisherFactory` that lazily builds a viem `PublicClient` + `WalletClient` + `PluginRegistryPublisher`, `resolveCliPassword`).
- `client/src/cli/commands/harnesses.ts` exposes `list | add | remove | enable | mode | status` — all config-side, no chain writes. `add` already verifies a manifest against `cfg.trustedImplSigners`; this is the "local-only" trust path that the issue says must keep working.
- The ERC-8004 reputation surface (`endorse`, `warn`, `respond`, `revoke-feedback`, `list-feedback`) lives in `client/src/erc8004/reputation.ts` as `ReputationRegistryClient` (`giveFeedback`, `respondToFeedback`, `revokeFeedback`, `readFeedback`, `readAllFeedback`, `getSummary`, `getClients`), but **no CLI verb wraps it** today. The class is consumed only by the engine's evaluator-delivery feedback hook (`submitEvaluatorFeedback`), constructed in `client/src/main.ts` (lines ~2098-2134).
- The plug-in metadata registry write surface (`PluginRegistryPublisher`, `publish` / `revoke` on `IdentityRegistry.setMetadata`) is in `client/src/erc8004/plugin-registry.ts`. There is no plug-in *discovery / read* CLI yet — discovery happens only inside the daemon, via the shared `DiscoveryAPI` (`client/src/discovery/factory.ts`).

So the work in #117 is: **introduce the missing network-trust CLI verbs and wire them to the same real-dependency builders the daemon and `solver-plugins publish/revoke` already use, using the same dependency-injection shape so tests can mock at the publish/read boundary.** Nothing in the existing code base needs to be moved off a stub — the stub-vs-real distinction in the issue refers to the *absence* of network plumbing, not to a stub object that exists today.

## Chosen approach

**Extract the real-dependency builders that already exist, package them as injectable factory functions, and add CLI verbs that consume them through `Partial<Deps>` injection — exactly the pattern in `client/src/cli/commands/solver-plugins.ts` (`PRODUCTION_DEPS` + `createSolverPluginsCommand(deps: Partial<…>)`).**

The reusable building blocks already in tree:

1. `createCliSignerContext(opts)` in `client/src/cli/execution-context.ts` — single helper that resolves the password, loads config, decrypts the mnemonic keystore, derives the master signer, opens the `FleetStateStore`, and builds a `PublicClient` + `WalletClient`. Already used by `jinn claim-rewards` and `jinn fleet-scale`. Returns a typed-envelope failure for missing keystore / wrong password / no fleet keystore / bootstrap-incomplete.
2. `pinFileToIpfs` in `client/src/adapters/mech/ipfs-pinfile.ts`, plus `uploadToIpfs` / `fetchFromIpfs` in `client/src/adapters/mech/ipfs.ts` — canonical IPFS write/read using `config.ipfsRegistryUrl` / `config.ipfsGatewayUrl`.
3. `PluginRegistryPublisher` in `client/src/erc8004/plugin-registry.ts` — Safe-routed `setMetadata` writes for `plugin:<cid>` and revocation records.
4. `ReputationRegistryClient` in `client/src/erc8004/reputation.ts` — `giveFeedback` / `respondToFeedback` / `revokeFeedback` / read paths. Already supports Safe-routed writes.
5. `getReputationRegistryAddress(chainId)` and `IDENTITY_REGISTRY_ADDRESSES` — canonical 0x8004… deployments per chain.
6. `createDiscoveryAPI(config, deps)` in `client/src/discovery/factory.ts` — primary HTTP/Ponder + optional on-chain floor for reads.
7. `FleetBootstrapper.ensureStage1(password)` — already invoked by `publishHandler` / `revokeHandler` to lazily complete Stage 1 (Safe + agent NFT mint) before any chain write.

The new CLI handlers reuse all of these unchanged. The dependency-injection shape mirrors `SolverPluginsDeps` in `solver-plugins.ts`:

```ts
interface NetworkTrustDeps extends BaseCommandDeps {
  bootstrapperFactory: (cfg) => Pick<FleetBootstrapper, 'ensureStage1'>;
  reputationClientFactory: (args: {
    reputationRegistryAddress: Address;
    safeAddress: Address;
    rpcUrl: string;
    network: JinnOnchainNetwork;
    earningDir: string;
    password: string;
  }) => Pick<ReputationRegistryClient,
    'giveFeedback' | 'respondToFeedback' | 'revokeFeedback' |
    'readAllFeedback' | 'getSummary' | 'getClients'>;
  discoveryApiFactory: (cfg) => DiscoveryAPI;
  ipfsFetch: typeof fetchFromIpfs;  // for plug-in payload introspection
  resolveCliPassword: typeof defaultResolveCliPassword;
  now: () => number;
}
```

The production `reputationClientFactory` mirrors the lazy-mnemonic-decrypt pattern already in `solver-plugins.ts:PRODUCTION_DEPS.publisherFactory` (lines 94-142): synchronous return, lazy `walletClient` construction so the password is only ever consumed once and the factory itself stays cheap to call. Tests substitute the whole factory with a `vi.fn()` and never reach this path — exactly how `solver-plugins-publish.test.ts` already operates.

## CLI subcommands to introduce, and the dependency each needs

The acceptance criteria in #117 imply this verb surface. We house all of them under `jinn solver-plugins …` to keep the trust action surface flat and discoverable; alternate placement (`jinn trust …`) was considered and rejected because the verbs all act on agent NFTs that are already addressed by SolverPlugin and Harness records.

| Subcommand | Action | Dependency it receives |
|---|---|---|
| `solver-plugins endorse <pluginCid> [--score N --score-decimals N --tag1 <s>]` | Submits positive feedback on the plug-in builder's agentId via `ReputationRegistryClient.giveFeedback`. `manifestRef = "plugin:<cid>"`, `manifestHash = keccak256("plugin:<cid>")`. | `bootstrapperFactory` (Stage 1 ensure), `reputationClientFactory` (real client), `resolveCliPassword`. |
| `solver-plugins warn <pluginCid> --reason <text>` | Mid-range score (`score=50, scoreDecimals=2`) plus the reason captured in a feedback URI. Same `giveFeedback` path; `tag1 = "warning"`. | Same as `endorse`. |
| `solver-plugins block <pluginCid> --reason <text>` | Score=0 feedback (`tag1 = "block"`) **and** appends the plug-in CID to a new local `cfg.solverPlugins.blockedCids[]` list so the daemon refuses to load it. The local config write must succeed even when the network publish fails — see "Failure modes" below. | Same as `endorse`, plus direct config-file write via `writeConfigFile` (already in `harnesses.ts`). |
| `solver-plugins review <pluginCid> --score N --score-decimals N --tag1 <s> [--response-to <feedbackIndex>]` | General-purpose `giveFeedback` (or `respondToFeedback` when `--response-to` is set). | Same as `endorse`. |
| `solver-plugins list-feedback <pluginCid> [--client <addr>] [--include-revoked]` | Read-only `readAllFeedback` against the agentId behind the plug-in record. Resolves agentId via the indexer (DiscoveryAPI envelopes by `plugin:<cid>` metadataKey) and falls back to an on-chain `IdentityRegistry.Registered` scan when the indexer is unavailable. | `discoveryApiFactory`, on-chain read via `createJinnPublicClient` only — no signer, no password. |
| `solver-plugins discover [--solver-type <id>] [--builder <agentId>]` | Read-only query for published plug-in records via DiscoveryAPI (Ponder GraphQL on metadataKey prefix `plugin:`). Optional `--from-block` falls back to `eth_getLogs` against `IdentityRegistry.MetadataSet` if the indexer is unreachable. | `discoveryApiFactory`, `ipfsFetch` (to dereference each `pluginCid` to its `PluginPayload` for display). No signer needed. |
| `solver-plugins status <pluginCid>` | Read-only summary: current `plugin:<cid>` payload (revoked or active), `ReputationRegistry.getSummary` for the builder's agentId, count of blocking entries on the local config. Composes `discoveryApiFactory` + `reputationClientFactory` in read-only mode (no `walletClient`). | `discoveryApiFactory`, read-only public-client (no password required). |

`status` and `list-feedback` MUST work without `JINN_PASSWORD` set, because they're pure reads. The dependency factories support this: `ReputationRegistryClient` allows `walletClient: undefined` for read-only consumers, and `createCliSignerContext` is only invoked for verbs that need a signer.

Helper modules to add:

- `client/src/cli/commands/solver-plugins-feedback.ts` — `endorseHandler`, `warnHandler`, `reviewHandler`, `respondHandler`. Shares the same handler shape as `publishHandler` / `revokeHandler`: top-level `resolveCliPassword`, then `loadConfig`, then `ensureStage1`, then `reputationClient.giveFeedback`.
- `client/src/cli/commands/solver-plugins-block.ts` — `blockHandler`. Same flow as `warnHandler` *plus* an unconditional local `cfg.solverPlugins.blockedCids` append, written even when the network publish fails. The handler returns one of three JSON envelopes: `{ blockedLocal: true, txHash }`, `{ blockedLocal: true, networkPublishError: { code, message } }`, or `{ error: { code: 'config_write_failed', … } }`.
- `client/src/cli/commands/solver-plugins-read.ts` — `listFeedbackHandler`, `discoverHandler`, `statusHandler`. No password resolution; uses `discoveryApiFactory(config)` and an unsigned `createJinnPublicClient(config.rpcUrl, …)`.

These new handlers slot into the existing dispatcher in `solver-plugins.ts` (the `if (subverb === '…')` block) with the same `parseArgs` + `writeJson` shape `publish` and `revoke` already use.

## Failure modes the CLI must report

Every new handler returns a single-line JSON envelope on stdout. Error codes (matching existing conventions in `solver-plugins-publish.ts`):

1. **Missing keystore password (write verbs only).** `code: keystore_missing`, message names `JINN_PASSWORD`, `--password-fd`, and the keystore-password file. Pre-resolved before any other work (mirrors `publishHandler` line 51-61).
2. **Wrong password / corrupt keystore.** `code: invalid_invocation`, message "Failed to decrypt the mnemonic keystore (wrong password?)". Bubbled from `decryptMnemonic` inside the lazy factory.
3. **Missing RPC URL or bad RPC.** `code: transient_error` with the underlying viem RPC error in `details.cause`. Surfaced when the lazy `walletClient` write throws. Mirrors `createCliExecutionContext` lines 180-194.
4. **Missing IPFS registry URL (discover only — when payload deref is requested).** `code: invalid_invocation`, message "discover requires `ipfsRegistryUrl` in config or `JINN_IPFS_REGISTRY_URL` env var to fetch plug-in payloads. Re-run with `--no-payload` to list CIDs only." `config.ipfsGatewayUrl` already has a default (`https://gateway.autonolas.tech`); this error fires only if the operator overrode it to empty.
5. **Stage 1 incomplete (write verbs).** `code: ensure_stage1_failed` with the bootstrapper's hint (typically "fund the master EOA with ETH and re-run"). Mirrors `publishHandler` lines 124-130.
6. **Fleet identity missing after Stage 1 (write verbs).** `code: fleet_identity_missing` — re-run after the next stage1 cycle. Mirrors `publishHandler` lines 132-142.
7. **AgentId unresolvable (`list-feedback`, `endorse`, `warn`, `block`, `review`).** When the plug-in CID has no matching `plugin:<cid>` record indexed: `code: agentid_unresolvable`, message names the CID and the discovery mode that was tried. `status` returns `{ status: 'not_published' }` instead of erroring — it's the answer to a read.
8. **Self-feedback (`endorse`, `warn`, `review`).** The contract reverts when the caller is the builder. `code: self_feedback_not_allowed`, hint: "Use a different operator agent NFT, or skip endorsement for plug-ins you publish yourself."
9. **Network publish failed but local config was written (`block` only).** `code: blocked_locally_only`, with `details.networkError.{code,message}`. The exit code remains `0` because the local effect — the daemon will not load the plug-in — did succeed; the warning surfaces the network gap so the operator knows the public-trust effect did not land.
10. **Indexer unreachable (`discover`, `list-feedback`, `status`).** When the configured DiscoveryAPI raises `DiscoveryUnavailableError`: `code: discovery_unavailable`, message names the configured mode and URL, hint suggests setting `discovery.fallbackToOnchain=true` (with the caveats from `CLAUDE.md`'s discovery section).
11. **Generic publish failure.** `code: publish_failed` with the underlying error message. Mirrors `publishHandler` lines 191-199.

## Local-only effects that must NOT require network

- `harnesses add / remove`: already local-only against `cfg.trustedImplSigners` / `cfg.harnesses.externalImpls`. Untouched by #117.
- `solver-plugins block`: the *config-write half* of `block` must succeed even when the network `giveFeedback` fails. Order of operations: try the network call first; whether it succeeds or fails, append `<pluginCid>` to `cfg.solverPlugins.blockedCids` and `writeConfigFile`. Only a config-write error is fatal. Tests cover both the network-ok and the network-fail-but-local-ok paths.
- All `show / validate / pack` verbs remain entirely local — no change.

## Test boundary

Mock at the dependency-factory boundary, never on the `viem` clients themselves. Specifically:

- Substitute `bootstrapperFactory`, `reputationClientFactory`, `discoveryApiFactory`, `ipfsFetch`, and `resolveCliPassword` with `vi.fn()` shims. This is exactly what `client/test/cli/commands/solver-plugins-publish.test.ts` (lines 80-128) already does for `publish`; we keep that pattern verbatim.
- The injected `ReputationRegistryClient` mock implements only the methods the verb under test touches (`giveFeedback`, `readAllFeedback`, `getSummary`, etc.) — matching the `Pick<…>` shape in the deps interface.
- A small set of in-tree fixtures: a temp `config.json` (`withTempConfig` already exists in `solver-plugins-publish.test.ts`), a fake `pluginCid`, a deterministic password mock.

Coverage targets per verb:
- Happy path: pipeline reaches the mock and emits the expected envelope.
- `keystore_missing`: `resolveCliPassword` returns `{ ok: false }` → handler exits 1 with the expected code.
- `ensure_stage1_failed`: bootstrapper mock returns `{ ok: false }` → handler exits 1 with `ensure_stage1_failed`.
- `block`-specific: network throws, config write still happens.
- `list-feedback` / `discover` / `status` (no signer): handler runs without `JINN_PASSWORD` set, and exits 0 against a mocked `discoveryApiFactory` that returns canned envelopes.
- `discovery_unavailable`: factory's `queryEnvelopes` throws `DiscoveryUnavailableError` → handler exits 1 with the documented code.

One Anvil-level integration test, mirroring `client/test/cli/commands/solver-plugins-publish.anvil.test.ts`, exercises `endorse` end-to-end against a forked chain with a real Safe transaction — confirms the production `reputationClientFactory` actually round-trips a write via Safe. This stays at the Tier 3 (slow, opt-in) level so the unit suite remains fast.

## What stays out of scope

- Daemon-side hot-reload of `cfg.solverPlugins.blockedCids`. The block list is read at daemon startup; operators must restart the daemon for `block` to take effect on the *currently-running* daemon. Hot-reload is its own feature; flagging it as a follow-up issue is the right move.
- A `jinn trust` top-level command group. Verbs land under `solver-plugins` to keep the surface flat; a `harnesses endorse / warn / …` mirror surface for harness builders is a clean follow-up.
- Operator-app (dashboard) buttons for these verbs. They will compose the CLI handlers via the existing daemon API in a follow-up; the CLI is the load-bearing surface for #117.
- The `consensus`-tier feedback aggregation and any new ABI. Reuses the existing 0x8004… deployments unchanged.
