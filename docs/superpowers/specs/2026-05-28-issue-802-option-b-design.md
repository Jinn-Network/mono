# Issue #802 — swe-rebench-v2 generator: re-post on claim-budget exhaustion (Option B)

- **Date:** 2026-05-28
- **Author:** opus (design stage, `feat/802-repost-on-claim-budget-exhaustion`)
- **Issue:** [#802](https://github.com/Jinn-Network/mono/issues/802)
- **Amends:** DR-2026-05-22-a §Decision (4)–(6) via a short "superseded by #802" note (repost trigger becomes exhaustion-driven, not time-expiry)
- **Shape:** feat

## Approach

Promote **Option B** (deferred-not-rejected in DR-2026-05-22-a §Alternatives, line 199–202): one live posting per instance, re-posted only when its on-chain claim slots are actually exhausted, detected via the indexer. The chosen trigger reuses the read path the generator already pays for. `DiscoveryAPI.findClaimableTasks` already computes per-task `attemptCount` and `maxClaims` (`client/src/discovery/http.ts:670–697`; on-chain floor `client/src/discovery/onchain.ts:781–813`), and the indexer's `task` table carries `maxClaims` plus a one-to-many join to `attempt` (`packages/indexer/ponder.schema.ts:71,121–147`). "Exhausted" is therefore observable as `attemptCount >= maxClaims` on the live posting's taskId — exactly the gate `findClaimableTasks` uses to drop a fully-claimed task (`http.ts:677`). The cleanest shape is to add a sibling DiscoveryAPI query — call it `getInstanceClaimCounts({ manifestCid })` — modelled on the existing `getInstanceSuccessCounts` (`http.ts:1015–1050`, `types.ts:265–294`): it pages the SolverNet's tasks, sums `attempt` rows per taskId, and returns the live posting's consumed-vs-`maxClaims` status. The map key must be `instance_id`; since the on-chain `task`/`attempt` tables do not carry `instance_id` (only `verdictEnvelopeMeta` does, via IPFS enrichment — `ponder.schema.ts:633–651`), the generator joins on its **local** `generator-state.json` ledger, which already knows the (instance_id → posted taskId) mapping it just created at post time. The generator should record the posted on-chain taskId per instance in `_swe-rebench-v2-state.ts` (a new `last_task_id` field beside the existing `{ posted, successful, last_posted_at }`, `_swe-rebench-v2-state.ts:12–16`) so the exhaustion query is a direct per-task lookup rather than an IPFS-dependent re-derivation. On indexer outage the tick aborts exactly as the existing `getInstanceSuccessCounts` reconciliation does (`swe-rebench-v2.ts:603–620`) — falling through to local-only counts is the bug, not the fallback.

## How the five acceptance criteria are satisfied

`classifyPoolTask` / `selectNextPostingCandidates` (`swe-rebench-v2-auto.ts:62–138`) change from a time-window classification to a claim-budget one. The `live` vs `repostable` distinction stops being `now − last_posted_at >= posting_window_ms` (`swe-rebench-v2-auto.ts:70`) and becomes: a posting is `live` while its on-chain `consumedSlots < maxClaims`, and `repostable` once `consumedSlots >= maxClaims` **and** `successful < N_target_successes`. **AC#1** (re-post within one tick on exhaustion) and **AC#4** (exhaustion from on-chain/indexer counts, not the timer) both fall out of this: when a posting's slots are all consumed and successes are still short, the instance classifies `repostable` on the very next tick and is re-posted with a fresh `claimPolicyForPosting(genConfig, N − successful)` budget — the per-posting `maxClaims = N − successes` sizing (`swe-rebench-v2.ts:651,685`, DR-2026-05-22-a §Decision (2)) is unchanged. **AC#2** (stop at N) is unchanged — `successful >= N_target_successes ⇒ saturated` stays the first branch of `classifyPoolTask` (`swe-rebench-v2-auto.ts:67`). **AC#3** (retry hard instances indefinitely) removes the abandon cap: the `posted >= N_max_postings_per_task ⇒ abandoned` branch (`swe-rebench-v2-auto.ts:68`) and the in-batch cap (`swe-rebench-v2-auto.ts:131–134`) are dropped, and `N_max_postings_per_task` becomes opt-in defaulting to unbounded (`Infinity`) in `DEFAULT_GENERATOR_CONFIG` (`swe-rebench-v2-auto.ts:27–33`). Because exhaustion is now the *only* repost trigger and a re-post only fires when slots are genuinely spent, there is no time-driven churn to bound, so the cap's original purpose (cut losses on a churning instance) no longer applies.

## AC#5 (revised): time trigger removed; escrow reclaim is out of scope

Scope was trimmed during design review (2026-05-28). The original AC#5 spoke of "preserving escrow reclaim," which presumed reclaim was a live, timer-driven behaviour. It is not. The repost trigger is the only thing that moves.

Each posting keeps its normal on-chain claim-window deadline (`claimWindowEnd`, derived from the existing `posting_window_ms`, default 1 d) — that deadline is the task's on-chain lifetime and is **unchanged**. What changes is that the generator's *repost decision* no longer keys off a local `last_posted_at + posting_window_ms` timer; it keys off observed claim exhaustion (see Approach).

Escrow reclaim is explicitly **out of scope**. `refundUnusedTaskBudget` exists on JinnRouterV3 (`contracts/src/staking/JinnRouterV3.sol:313–348`) but is **never called by the client today** (verified: no call site in `client/src` or `packages` outside tests). Escrow on never-claimed slots is already left locked, independent of this change, so removing the timer-as-repost-trigger regresses nothing. Incidentally, Option B strands *less* escrow than the timer model — it reposts only after slots are genuinely consumed, instead of abandoning half-claimed postings on a 24 h timer. Wiring reclaim is a separate, pre-existing concern for its own issue. This design does **not** touch `expireAttempt`, does **not** decrement `claimCount`, and refunds nothing — the one-way claim budget (claim = payment, anti-Sybil; DR-2026-05-25 rejected 2026-05-26) is fully preserved.

## Trade-offs considered

(1) **Per-instance claim query vs reuse of `findClaimableTasks`.** A dedicated `getInstanceClaimCounts` keyed by the generator's known taskIds is cheaper and more direct than re-running the full claimable scan; it mirrors `getInstanceSuccessCounts` one-for-one, so the indexer-outage / floor semantics are already settled (`types.ts:280–294` — the floor returns empty and `withFallback` propagates the error rather than under-counting). (2) **Local taskId ledger vs IPFS instance-id join.** Recording the posted taskId locally avoids a dependency on `verdictEnvelopeMeta` enrichment (which lags and is success-only); the generator is the authority on what it posted, so this is both simpler and more correct. (3) **Window churn vs exhaustion exactness.** Option B's whole point (DR-2026-05-22-a line 199–201) is exact-N with zero time-window churn; the cost — an indexer dependency in the repost path — is already paid by the per-tick `getInstanceSuccessCounts` reconciliation (#669), so Option B no longer carries a *new* cost relative to the shipped generator. (4) **Keep `posting_window_ms` as the on-chain claim-window deadline.** The field stays (each posting needs an on-chain deadline); only its role as the *repost trigger* is removed. Renaming it to reflect the narrowed role is optional churn (touches manifest schema + SPA templates) and is left to the plan's discretion — minimal diff favours keeping the name.
