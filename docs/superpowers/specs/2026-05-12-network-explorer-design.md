## 1. Purpose

A public, **daemon-free** web surface that makes the Jinn network legible: what work the network has done and how operators and SolverNets perform — and, for SolverNets that define a score, **how a self-improving agent's performance is trending over successive tasks/iterations/checkpoints**. It reads off the privately-operated Ponder indexer shipped as `jinn-mono-280n` (`spec/2026-05-11-discovery-api-and-shared-indexer.md`), through a read surface shaped for aggregate queries — not by coupling to raw Ponder internals.

The Project boards show the plan; this shows the network actually working. It is also the first real external consumer of the indexer. (A note on the "inert rollup entities": the ERC-8004 payload-schema v2 work *names* `HarnessRollup` / `LanguageRollup` / `FreezeViolation` as future on-chain-fed entities, but the v2 payload that would feed them — `(implName, codeDigest, modeFlag)` on-chain — is not yet being written, so the explorer derives the same dimensions from the IPFS execution envelope instead, via the enrichment pass in §4.2. When v2 ships, those entities can be re-pointed at the on-chain source with no consumer change.)

## 2. View scopes

Three scopes, each filterable/groupable by the dimensions in §4:

- **Network** — totals across everything: tasks posted / attempted / settled, JINN distributed (cumulative + recent rate), distinct active operators, number of SolverNets running, overall verdict-success rate, composition (share of attempts by harness / mode / model).
- **Per-SolverNet** — scoped to one `manifestCid`: that net's activity KPIs, plus — if the SolverNet defines a scoring metric — the **Learning panel** (§5) with operator leaderboards split train/frozen.
- **Per-operator** — one operator across the SolverNets they participate in: their scores, settled-task contribution, JINN earned, dominant harness/mode, per net.

**v1 (`jinn-mono-uy6v`) ships exactly one SolverNet — SWE-rebench v2.** At N=1 the Network view and the Per-SolverNet view are the same data; there is nothing to aggregate *across*. `jinn-mono-rdod` is precisely "this explorer, with the SolverNet filter pinned to SWE-rebench v2" — not a separate artifact. The multi-net pages (SolverNets index, cross-net operator leaderboard, network rollups that sum nets) are designed here but only have data to chew on once a second SolverNet exists; they land as a follow-up child. `jinn-mono-rdod` remains the tracking bead for the `uy6v` release gate and gains a dependency on the relevant explorer children.

`jinn-mono-xmq` (CLI aggregated history) is adjacent, not subsumed — different surface (one operator's own CLI history vs. the public web aggregate); may share the indexer as a data source later, nothing to resolve here.

## 3. Read path, deployable shape, hosting

**One indexer, one schema; the explorer reads the indexer's *public* surfaces, not the daemon's `DiscoveryAPI`.** The daemon's `DiscoveryAPI` (`spec/2026-05-11-...` §5) stays daemon-shaped — "what is actionable for me, the operator daemon, right now": point lookups, operator-filtered, claim-window-windowed, polled constantly, latency-sensitive, narrow. The explorer does *not* extend it. It instead consumes the indexer's two public read surfaces (both versioned, both stable):

1. **Ponder's auto-generated GraphQL API** — the standard onchain-analytics read path. A typed, paginated, filterable query layer over the schema entities. Used for everything that is "list these entities, filtered/sorted/faceted, page through them": leaderboard rows under arbitrary facet filters, the attempt feed, the checkpoint list, an operator's history. GraphQL gives the explorer's faceting for free — the schema *is* the API.
2. **Custom aggregation routes (`/explorer/*` JSON, Hono routes mounted alongside the GraphQL endpoint)** — for the things GraphQL can't express: rolling rates, server-bucketed time series (the learning curve), cross-entity rollups, the headline KPI bundles. These are thin SQL queries against the same Postgres the indexer already owns.

The ticket's "DiscoveryAPI only" relaxes to: *the explorer reaches only the indexer's public GraphQL + `/explorer/*` surfaces — never past them* (no direct Postgres, no scraping Ponder's internal tables, no on-chain RPC of its own). The thing kept single is the **Ponder schema + handlers**; the read surfaces are thin layers over it. Same source data as the daemon (JinnRouter events + ERC-8004 metadata/reputation + distribution-contract events + IPFS-resident envelopes), different query shapes, different consumer.

**The explorer ships inside `@jinn-network/indexer`.** The indexer is already a required, running service (privately operated by the daemon's current maintainer per `spec/2026-05-11-...` §8.1 — not protocol infrastructure). It already exposes HTTP and Ponder lets custom Hono routes mount alongside the auto-GraphQL endpoint. So the indexer package gains:

- the explorer **static SPA, served at `/`**;
- the **`/explorer/*` aggregate + faceted JSON routes**.

**One deployable — the one that already exists.** The "team-hosted canonical instance" is the maintainer's existing indexer instance; **anyone who runs `@jinn-network/indexer` serves an explorer for free**, and the static SPA can be pointed at any indexer URL. This matches "Jinn runs no runtime infrastructure for operators" (`spec/2026-05-08-vps-first-operator-deployment-design.md`) and the headless-brand posture (`BRAND.md`): the explorer is one narrative skin riding a participant-run service; another operator may re-skin their own. The operator app may *link out* to a canonical explorer URL; it does **not** embed it (embedding would re-introduce a daemon dependency and a second render path). SPA source lives in the repo under `packages/indexer/explorer/` (or `packages/explorer/` built into the indexer's static dir — pick at impl).

**No "RPC floor" for the explorer.** The on-chain `OnchainDiscoveryAPI` floor is a *daemon liveness* mechanism (keep the operator working during an indexer outage). A public dashboard has no such requirement: if the indexer is down, the explorer is down or stale, which is acceptable. The SPA shows a staleness banner with `lastIndexedBlock` / `updatedAt`. A direct-RPC fallback for the explorer is possible but slow and not worth it — explicitly deferred. (x402 never enters the picture — the explorer shows refs and counts, never gated bytes.)

**Onchain-analytics conventions.** Standard practice for indexer-backed dashboards, applied here:

- **The freshness contract.** Every onchain dashboard must answer "as of when?" — analogous to a subgraph's `_meta { block { number } }`. Every GraphQL response and every `/explorer/*` payload echoes `lastIndexedBlock`, `lastIndexedAt`, and a `behindHead` lag (Ponder's `/status`/`/ready` is the source). The SPA renders this in the status bar always, and as a banner when the lag exceeds a threshold or `/ready` is non-200 ("indexer degraded — showing data as of block N").
- **Server-side time-bucketing.** Time series (learning curve, activity-over-time, JINN-flow) are bucketed on the server — by block range or by hour/day — never by shipping raw events to the client to aggregate. Bucket granularity is a query param with sane caps.
- **Cursor pagination, not offset.** Entity lists (leaderboard, attempt feed, history) page by sequence-id / block-number cursors — Ponder's GraphQL gives Relay-style cursor pagination out of the box. Offset pagination breaks under new data arriving at the head; cursors don't.
- **Reorg tolerance.** Reorgs are the indexer's problem (Ponder handles them); the explorer's job is to not jank when a near-head metric value shifts slightly between polls — render number changes without layout shift (`tabular-nums`, fixed column widths), and optionally mark values derived from unfinalized blocks with a small "live" affordance. Don't show stale-then-snap; show the new value smoothly.
- **HTTP caching.** Aggregation routes compute from Postgres on request with a short server-side cache (~30–60 s on heavy rollups — leaderboards, learning curves; shorter or none on small KPI reads) **and** set `Cache-Control: public, max-age=30, stale-while-revalidate=60` + an `ETag` keyed on `lastIndexedBlock`, so a CDN / the browser absorbs the traffic spike when a checkpoint score moves and everyone refreshes. GraphQL responses get the same treatment via persisted-query GETs where it helps. Materialized rollup tables vs compute-on-read is an impl decision (default: compute-on-read; promote to materialized if the leaderboard/learning queries are too slow at scale).
- **No client-side chain reads.** The SPA never makes its own RPC/`ethers` calls — it is purely indexer-fed. The on-chain RPC floor is a *daemon* mechanism (above), not an explorer one.

## 4. Data model — additive Ponder schema

The Ponder schema (`spec/2026-05-11-...` §7: four entities — `Task`, `Attempt`, `SolverNetManifest`, `Envelope`) grows **additively**. Nothing existing is renamed or restructured. Two tiers: **on-chain-derivable** entities (no IPFS) ship in `ebu7.2`; **envelope-enrichment** entities (need an IPFS fetch of the execution envelope) ship in `ebu7.6` and require resolving how an attempt links to its envelope (resolved — see below).

### 4.1 On-chain-derivable (ebu7.2 — no IPFS)

| Entity | Source | Powers |
|---|---|---|
| `Task`, `Attempt` *(existing)* | `JinnRouter.TaskCreated` (`creator, taskId, manifestDigest, taskCidDigest, maxClaims, requiredVerdicts, ...`), `TaskAttemptCreated`, `SolutionDeliveryClaimed` | tasks posted, settled-task count (`finalized`), distinct active operators (`attempt.operator`), throughput |
| `Task.refunded` *(wire it up — existing field, not yet populated)* | `JinnRouter.TaskBudgetRefunded(taskId, creator, solutionAmount, verdictAmount)` — this event **does** exist (the schema comment saying it doesn't is stale) | refunded-task accounting; correctness of "settled" counts |
| `SolverNetManifest` *(existing)* | `IdentityRegistry.MetadataSet` (`solvernet-manifest:*`) | SolverNets running, per-net scoping |
| `Verdict` *(new)* | `JinnRouter.VerdictDeliveryClaimed(evaluator, requestId, taskId, attemptIndex, verdictIndex, uint8 verdictCode)` — `VerdictCode {None=0, Pass=1, Fail=2, Invalid=3, Unresolved=4}`; mirror `TaskCoordinator.recordVerdict` to derive per-attempt finalization (`validVerdictCount == requiredVerdicts` ⇒ `passed = passVerdictCount >= passThreshold`) | **verdict-success rate, resolved-rate, the Learning-curve rolling rate, quality-first leaderboards.** The SWE-rebench *float* score stays IPFS-only; the binary "test suite passed" = `verdictCode==Pass`, which is what "resolved" means. |
| `RewardDistribution` *(new)* | `JinnDistributor.Claimed(serviceId, multisig, operatorMinted, daoMinted, totalEntitledOperator, totalEntitledDao)` (`contracts/src/jinn/distribution/JinnDistributor.sol`; one contract, three weighted channels `wTaskCreation`/`wSolutionDelivery`/`wVerdictDelivery` — the per-channel breakdown is **not** in the event; reconstruct it from per-operator JinnRouter activity counts: `TaskCreated` by creator, `SolutionDeliveryClaimed` by operator, `VerdictDeliveryClaimed` by evaluator) | JINN distributed — network-wide and per-operator (keyed by `serviceId`/`multisig`), cumulative + rate; per-channel split via the reconstructed activity counts |

### 4.2 Envelope-enrichment (ebu7.6 — IPFS fetch of the execution envelope)

The link: the `Envelope` entity (existing) already indexes `IdentityRegistry.MetadataSet` events with key `envelope:<cid>` (kind=`envelope` = execution evidence). The enrichment pass fetches each such envelope's IPFS body and reads its `task.requestId` (the `jinn.execution.v1` envelope records the originating MechMarketplace `requestId` — `client/src/types/envelope.ts` `TaskProvenanceSchema`), joining it to `Attempt` by `requestId`. No call-trace decoding needed. Harness identity / mode / `codeDigest` / plugins / model all live in the envelope's `executor` block (`client/src/types/envelope.ts`).

| Entity | Source (IPFS body of indexed `Envelope` rows, kind=`envelope`) | Powers |
|---|---|---|
| `AttemptEnvelopeMeta` *(new)* | `executor.implName`/`implVersion` (harness), `executor.codeDigest`, `executor.mode` (`train`/`frozen`), `executor.plugins[]`, `sessionProvenance.originatingTool` (≈ model/agent), `solverType`, `evidenceTier`, `executor.source` published flag; joined to `Attempt` by `task.requestId` | harness breakdown, **train/frozen split**, plugin/model facets, evidence-tier facet, source-published flag |
| `HarnessRollup` *(new — derived rollup over `AttemptEnvelopeMeta` × `Verdict`)* | per-`(operator, solverNet, mode, codeDigest)` resolved counts; codeDigest-continuity threads | per-harness / per-mode / per-checkpoint-lineage success rates |
| `FreezeViolation` *(new — derived)* | a `mode=frozen` `AttemptEnvelopeMeta` whose `codeDigest` differs from the operator's established frozen digest for that SolverNet (`...agent-harness-solvernet...` §6.2 Layer 2) | freeze-integrity metric |
| `LanguageRollup` *(new — derived)* | solved-repo language, if exposed in the envelope `payload`/`sessionProvenance.repo` (SWE-rebench tasks are language-tagged); else absent | success-rate by language |
| `HarnessCheckpoint` *(new)* | published-checkpoint anchor — `IdentityRegistry.MetadataSet` with key prefix `harness.checkpoint:<sourceBundleCid>` (`...agent-harness-solvernet...` §7.1–7.2; the on-chain anchor mechanism is locked in the spec; pin the exact reserved-prefix string at impl) + the checkpoint manifest body on IPFS (`implStateDirCid`, `codeDigest`, `parentCheckpointCid`, `harnessPackage`); frozen-eval score = resolved-rate of `mode=frozen` attempts at that `codeDigest` | checkpoint timeline; per-checkpoint frozen-eval score; verified-frozen (source-bundle published) flag |

**Why `ebu7.6` is on the rdod critical path:** rdod's acceptance criteria include "train/frozen leaderboards both visible; clear which mode an operator is in" — mode lives only in the envelope, so the mode-aware Learning panel needs `ebu7.6`. The on-chain-only views (network KPIs, resolved-rate curve, leaderboards ranked by resolved-rate, JINN distributed, settled tasks) ship before it from `ebu7.2`/`ebu7.3`; if enrichment hits a snag the team can consciously ship the on-chain-only explorer as rdod-v1 with train/frozen flagged as a follow-up, but the default is to ship complete (see §10).

## 5. The Learning panel (per-SolverNet, when a score is defined)

This is the part the explorer exists for: making "as your agent learns, the network learns" observable. SWE-rebench v2 is the first SolverNet to fill it in; the panel generalizes to any SolverNet that (a) defines a scoring metric and (b) has a frozen-eval task distribution.

**What "the score" is for SWE-rebench v2:** the evaluator runs the upstream SWE-rebench v2 test suite in Docker and emits a verdict — resolved / not-resolved. The SolverNet's quality metric is **resolved-rate**.

**The aggregate we keep improving** is *not* "tasks done" — it is the **best frozen-checkpoint resolved-rate**. The train/frozen split is the measurement instrument: train-mode operators (`claude-code-learner` with Improve+Memory active) accumulate state across tasks; that state is periodically pinned as a published `HarnessCheckpoint` and run in **frozen mode** (envelope `executor.mode === 'frozen'`, fixed `codeDigest`) against the eval distribution. Frozen-mode resolved-rate at a fixed `codeDigest` is a clean, comparable score. Checkpoint v2 should beat v1. The staircase of frozen-checkpoint scores over time *is* the self-improving agent getting better.

**Data backing the panel (and what's on which path):** the **resolved-rate** itself — the headline number, the rolling-rate learning curve, the leaderboard sort — is **on-chain-derivable** from the `Verdict` entity (`JinnRouter.VerdictDeliveryClaimed.verdictCode == Pass`, with attempt finalization mirrored from `TaskCoordinator.recordVerdict`); it ships from `ebu7.2`/`ebu7.3`. The **mode (train/frozen) split, harness/codeDigest lineage, the checkpoint timeline, and freeze integrity** come from the IPFS envelope-enrichment pass (`ebu7.6` — `AttemptEnvelopeMeta` joined to `Attempt` by `task.requestId`; checkpoint anchors from `IdentityRegistry.MetadataSet` key `harness.checkpoint:*`); they land when `ebu7.6` does (which is on the rdod critical path — §4.2, §10). So the panel renders the resolved-rate curve + leaderboards from the first deploy; the train/frozen separation and checkpoint staircase light up with `ebu7.6`.

**Panel contents (per-SolverNet page = rdod, with the filter pinned to SWE-rebench v2):**

1. **Score, big** — current best frozen-checkpoint resolved-rate, with the delta vs the previous checkpoint.
2. **Learning curve** — x = tasks completed (toggle: iterations / wall-clock / checkpoint index); y = **rolling resolved-rate over the last K tasks** (K selector: 20 / 50 / 100 / all). One line per operator, or per checkpoint-lineage (codeDigest thread). Flat line = not learning; rising line = the loop works. This is the chart the whole explorer exists to make possible.
3. **Checkpoint timeline** — each published `HarnessCheckpoint` as a marker: its frozen-eval resolved-rate, n tasks, verified-frozen (source-bundle published — §6.2 Layer 4) or not. Click → checkpoint detail. The train-mode work *between* markers is what produced the lift.
4. **Train vs frozen leaderboards** — twin tables. Frozen = ranked checkpoints (the canonical "who's best"). Train = active learners, ranked by recent rolling resolved-rate. Min-attempts floor (§6). Low-volume operators in a separate "new / low-volume" strip with raw numbers, not ranked among leaders.
5. **Composition / activity (supporting, smaller)** — share of attempts by harness (`claude-code-learner` vs `codex-code-learner`) and mode; throughput; JINN distributed (per-channel split); `N_target_successes` saturation.
6. **Freeze integrity** — `FreezeViolation` count (target zero); verified-vs-unverified-frozen split.

**SolverNet without a defined score** → the panel degrades: headline = verdict-success rate, learning curve = rolling verdict-success rate, no checkpoint timeline, leaderboard ranks by verdict-success.

**Network-level headline at v1** = SWE-rebench v2's best frozen-checkpoint resolved-rate (one SolverNet). At N>1 there is no single cross-net score (SolverNets aren't comparable) — the Network view becomes a row per SolverNet, each with its own score + trend sparkline + a few KPIs.

## 6. Dimensions, leaderboards, faceting

The explorer is **faceted**, not a counter. Every aggregate view can be sliced / grouped / sorted by: **time window** and **SolverType** (on-chain — available from `ebu7.2`/`ebu7.3`); and — once `ebu7.6` enrichment lands — **harness** (`implName`), **harness version** (`implVersion`), **mode** (train/frozen), **language**, **evidence tier**, **plugin**, **model / originating-tool** (all envelope-sourced). The on-chain-only deploy (`ebu7.4a`) exposes the first set; the rest light up with enrichment.

**Leaderboard ranking** — quality-first by default: the SolverNet's own scoring metric where one is defined (e.g. SWE-rebench resolved-rate), else verdict-success rate. Throughput, settled tasks, JINN earned, dominant-harness are sortable columns but quality is the headline sort. Train and frozen are separate boards. **Small-sample guard:** operators below a minimum number of resolved attempts (`N` picked at impl, ~5–10) are listed but not ranked among leaders — they sit in a separate "new / low-volume" section with their raw numbers. (Considered and rejected for v1: Wilson lower-bound / Bayesian shrinkage as the sort key — more correct, more to explain in the UI; revisit if the simple threshold proves unsatisfying.)

**Visualizations** (all in the `DESIGN.md` idiom — see §7): activity-over-time as a stacked area by harness (or any facet); quality-by-dimension as a horizontal bar grouped by harness/model/language with the low-volume strip greyed; operator scatter — throughput (x) vs success-rate (y), dot colour = dominant harness, dot size = JINN earned, click → operator detail; "what's running" composition bar/table; JINN-flow cumulative line + per-channel stacked bar; freeze-integrity counts; the Learning panel of §5.

## 7. Visual & frontend implementation — bound by `DESIGN.md` + `BRAND.md`

### 7.1 Aesthetic direction (Protocol Brutalism, made concrete for a data explorer)

The canon is "Protocol Brutalism" (`DESIGN.md` §1) — for *this* surface, read it as **engineering schematic × terminal × the existing explorer UI kit**: deep night-blue ground (`#0c1628`), hierarchy carried by hairline 1px borders not shadows, two type voices only (Instrument Serif for *feeling* — the one big score number, page headlines, the `.wish` pull-quote; JetBrains Mono for *doing* — every label, value, table cell, axis), sky-blue ink (`#7aa7dc`) threading structure, lamplight gold (`#dcb866`) reserved for **one** point of emphasis per surface. On the per-SolverNet page that gold is **the headline score** and nothing else. Dense but legible — closer to controlled density than generous whitespace, because an explorer's value is in how much true signal fits on one screen. No dark-mode-neon, no purple-gradient SaaS chrome, no glassmorphism, no emoji, ever.

Built on the explorer UI kit (`docs/design/jinn-design-system/project/ui_kits/explorer/` — `Chrome` (`Logo`, `TopNav`, `SearchBox`, `StatusBar`), `Data` (`KPI`, `KPIRow`, `WishRow`, `TableHead`, `StatusChip`), `WishDetail` right-pane). Reuse those components and the tokens (`colors_and_type.css`, `foundations.css`); don't redraw. New components needed beyond the kit: the chart family (§7.3), the faceted filter bar, the leaderboard table (virtualized), the Learning panel.

### 7.2 Surface rules (from `DESIGN.md`)

- **Type:** axis labels, legends, column headers, status chips in ALL-CAPS JetBrains Mono, `letter-spacing: 0.14em`; all numerics use `font-variant-numeric: tabular-nums` so columns and changing values don't reflow. Values/body in mono, sentence case. Instrument Serif only for the big score (display/headline size) and page-level headlines. Sentence case for buttons/titles (`Bind vessel`, not `BIND VESSEL`). No sans.
- **Cards/panels:** `bg-elevated` (`#142340`), 1px hairline (`#1f3a66`), 10px radius (`--radius-3`), 24px padding. **Never nest cards** — the Learning panel is one card with internal hairline dividers, not cards-in-cards. Status chips: pill radius, status colour on border + text only, never a filled background. No `--shadow-float` on resting chrome; no `backdrop-filter: blur()`.
- **Motion:** linear, or `cubic-bezier(0.4,0,0.2,1)` as the rare exception — no spring/bounce/overshoot. One orchestrated page-load: KPI row reveals staggered (`animation-delay`), the headline score counts up (≤400ms), chart lines draw on via `stroke-dashoffset`. `prefers-reduced-motion` disables all of it and renders final state. The `.wish` slow-fade (≤600ms) is the only decorative motion.
- **Texture/atmosphere:** a very subtle grain/scanline overlay on the page ground is permitted (`DESIGN.md` allows textures); keep it near-invisible — atmosphere, not decoration. No gradients as decoration (the only exception in the system — protection gradients over imagery — doesn't apply here).
- **Lexicon** holds (tasks ≈ wishes, evaluators ≈ seers, *scrying* for logs, *ether* for the network state) — **except drop the metaphor wherever JINN amounts / money are shown:** plain "JINN distributed", not vow-language (`BRAND.md` operational rule; `DESIGN.md` §6).
- **Headless note:** the explorer ships one narrative skin; the doc and the indexer package README record that operators running their own indexer may re-skin their explorer per `BRAND.md` posture — protocol (the loop, the lexicon, the non-negotiables) fixed, visuals forkable.

### 7.3 Charts — engineering diagrams, not dashboard widgets

- **Library:** keep it light and controllable. `uPlot` for the high-density time series (the learning curve / activity-over-time can be thousands of points and uPlot stays fast and visually spare); hand-rolled SVG or `@visx/*` primitives (or Observable Plot) for the bespoke pieces (operator scatter, composition bars, checkpoint timeline). **Avoid** Chart.js / Recharts / Nivo defaults — their out-of-the-box look is exactly the generic-dashboard aesthetic the system rejects.
- **Styling:** 1px strokes; series colours from the fixed palette only (sky `#7aa7dc` for primary structure; gold `#dcb866` only for the single emphasised series/value on a surface; `vow-green` / `wane` / `break-red` / `seer-violet` for status series, on stroke + text, **never as filled areas**). Stacked areas use flat low-opacity palette fills, not gradients. Gridlines are dotted hairlines in `--border`. Axis ticks and labels in caps mono. Bars get `--radius-1` (4px) at most — softened-brutalist, not pillowy, not razor-square. Tooltips are hairline-bordered `bg-elevated` cards with mono content; no drop shadows beyond the permitted hard-offset.
- **Charts present in v1:** learning curve (rolling resolved-rate vs tasks/iterations/checkpoint index, K-window selector, line-per-operator or per-checkpoint-lineage); checkpoint timeline (markers with score + verified-frozen flag); activity-over-time (stacked area by harness or any facet); operator scatter (throughput × success-rate, dot colour = dominant harness, dot size = JINN earned, click → detail); composition bar/table ("what's running" — share by harness / mode / model); JINN-flow (cumulative line + per-channel stacked bar); freeze-integrity (counts; zero violations rendered affirmatively in `vow-green`).

### 7.4 Interaction & data-fetching patterns

- **URL state is the source of truth.** Scope (network / solvernet:`<cid>` / operator:`<addr>`), every active facet filter, the sort column+direction, the K-window, the time range, the open detail pane — all serialised into the query string, so **any view is a shareable permalink** and browser back/forward work. This is the defining UX property of an explorer (Etherscan, Dune, the Graph Explorer all do this); it's non-negotiable here. On load, the SPA hydrates state from the URL; on any control change, it replaces the URL and refetches.
- **GraphQL client:** light — `graphql-request` or `urql` over Apollo (an explorer that polls doesn't need Apollo's normalised cache); typed via codegen against the indexer's GraphQL schema. The `/explorer/*` aggregation routes are plain typed `fetch`. Batch the queries a page needs; don't waterfall.
- **Polling & staleness:** poll on a modest interval (e.g. 15–30 s); show the freshness state (§3) in the status bar always. On indexer-degraded, freeze the data and show the banner — don't blank the page.
- **Tables:** the leaderboard and feeds are **virtualized** (windowed rows) with a sticky `TableHead`, sort affordances as small carets, the min-attempts "new / low-volume" group rendered as a visually-separated section below the ranked rows, not interleaved. Row click → right-pane detail (`WishDetail`-style). Server does the sort/filter/paginate; the client never holds the full set.
- **Search / ⌘K** (the kit shows the hint, unwired): a command palette to jump to an operator address, a SolverNet, a checkpoint, a task CID. Designed here; **deferred** past v1 — nav + filter bar first.
- **States:** skeleton rows as hairline outlines on first load; empty states in plain mono copy (and `vow-green` when "empty" is *good* — zero freeze violations); error states inline, border + text in `break-red`.

### 7.5 Performance & accessibility budget

- Server-side aggregation and pagination mean the SPA's payload is bounded regardless of network size — it never ships 100k attempt rows. Initial JS budget: keep it lean (the design ethos *is* minimal deps — uPlot is ~50KB, `graphql-request` is tiny; resist a heavy chart lib).
- `tabular-nums` everywhere numeric; fixed column widths so polled updates don't reflow; respect `prefers-reduced-motion`; respect `prefers-color-scheme` only insofar as the canon is dark-first (light mode exists in the system but the canonical render is night).
- HTTP caching (§3) lets a CDN front the whole thing; the static SPA bundle is immutable-hashed and long-cached.

## 8. Decision records to file

- **DR — explorer rides the indexer service (one deployable), not a separate static site.** The indexer is already a required running service; the explorer ships inside `@jinn-network/indexer` as the static SPA at `/` + `/explorer/*` JSON routes. Rationale: zero new infrastructure; consistent with "Jinn runs no runtime infra for operators" and the headless posture; anyone running the indexer serves an explorer.
- **DR — explorer reads the indexer's public surfaces (auto GraphQL + `/explorer/*` aggregation routes), not an extended `DiscoveryAPI`.** `DiscoveryAPI` stays daemon-shaped; the explorer uses Ponder's auto-generated GraphQL for entity list/filter/sort/paginate and thin custom JSON routes for rollups/bucketed series. Rationale: genuinely different read concerns/consumers; GraphQL is the standard onchain-analytics read path and gives faceting for free; keeping the *schema* single is the DRY invariant, not the interfaces; cramming aggregate leaderboard queries into `DiscoveryAPI` bloats an interface with a clear narrow job. The explorer never reaches past these public surfaces (no direct Postgres, no Ponder internals, no own RPC).
- **DR — leaderboard ranking is quality-first (SolverNet score → verdict-success fallback) with a min-attempts floor and a separate low-volume section.** Rejected for v1: Wilson/Bayesian shrinkage as the sort key.
- *(Recorded, not a fresh DR — already resolved in the `jinn-mono-ebu7` notes:)* rdod **is** the explorer at N=1 scope (the SolverNet filter pinned to SWE-rebench v2), not a separate thing to subsume.
- **DR — verdict outcomes are read from on-chain `VerdictDeliveryClaimed.verdictCode` (a new `Verdict` entity), not from IPFS.** So resolved-rate / verdict-success / the Learning-curve rolling rate / quality-first leaderboard sort are on-chain-derivable and ship in `ebu7.2`/`ebu7.3`. The SWE-rebench *float* score stays IPFS-only and is not required for v1.
- **DR — train/frozen mode, harness identity, codeDigest lineage, freeze integrity, and the checkpoint timeline are read from the IPFS execution envelope (enrichment pass, `ebu7.6`), not from operator-local config and not from on-chain (the reputation payload v2 that would carry `modeFlag`/`implName`/`codeDigest` on-chain is not yet being written — Phase A.5).** Consequence: `ebu7.6` is on the rdod critical path (rdod's "train/frozen leaderboards" AC needs it). If enrichment is blocked, the team may consciously ship the on-chain-only explorer as rdod-v1 with train/frozen flagged as a follow-up — the default is to ship complete.
- *(Recorded — finding:)* `JinnRouter.TaskBudgetRefunded` exists, so `Task.refunded` is wireable (the indexer schema comment that says it doesn't is stale); and there is no four-reward-contracts split — a single `JinnDistributor` with three weighted channels.
