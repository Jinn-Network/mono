- **Date:** 2026-09-03 (rulings 1–3); 2026-09-04 (ruling 4).
- **Status:** Accepted — operator rulings in-session (Ritsu, 2026-09-03 and 2026-09-04) on design issue #3786. Enacted by the follow-up issues named in §Consequences; this record moves no files.
- **Owning docs:** [`docs/superpowers/specs/2026-07-30-jinn-platform-architecture.md`](../../docs/superpowers/specs/2026-07-30-jinn-platform-architecture.md) §5–§6; [`architecture/platform-packages.v1.json`](../../architecture/platform-packages.v1.json); [`docs/runbooks/jinn-network-profile-hosting.md`](../../docs/runbooks/jinn-network-profile-hosting.md).
- **Amends:** [DR-2026-07-30](./2026-07-30-platform-boundary-and-topology.md) on **one point only**: where the protocol is authored and presented. The triad, the boundary, the layering law, the inclusion test, the extraction gate, and the mono as implementation home are **unchanged**. Its named end state gains one refinement (§Decision 4). Also [DR-2026-08-04](./2026-08-04-spec-origin-and-vocabulary.md): the origin `spec.jinn.network`, the identifier law, and the namespace rules stand; what changes is the repository whose CI deploys the origin.

## Context

The protocol has no authored home. Its schemas, profile documents, vocabularies, facts profiles, and conformance fixtures live inside about a dozen package directories in this repository, each beside the TypeScript that implements it. The only standalone surface is a generated host repository whose README says nothing there is written by hand. An outsider cannot say what the protocol is without opening a twelve-thousand-file monorepo, and the reference implementation is the de facto specification — the failure mode the architecture spec §4 names.

DR-2026-07-30 read the comparables it cited (MCP, libp2p, Sigstore) as "do not split the kernel." Their repositories show something narrower: every one keeps the specification in a repository that is only the specification, and keeps implementations together. Separating the spec from its implementations is the pattern; fragmenting the implementation is the regret. The July ruling is right about the kernel and is not reopened.

On 2026-09-03 the operator ruled the direction in a design walk held outside this repository, and #3786 carried it here as direction for this repository's own decision process. In short: the interoperability floor is that any two implementations read each other's records, agree on validity and meaning, and find each other's records; settlement is out, the venue interface is in; the protocol is the record formats plus the wire; the spec is authored only in `Jinn-Network/spec`, released as signed digest manifests with per-document status, changed through numbered proposals, and its own CI deploys `spec.jinn.network`; the generated host repository is retired; vectors travel with the spec and a black-box conformance runner follows in its own repository; everything benchmark-related is the benchmarking product's; the mono starts as implementation-plus-network and ends as five repositories; the sequence is byte-identical import first, then pin, under the clean-repository rule.

Two facts established while preparing this record. First, `spec.jinn.network` answers every request with a redirect to a login page, so under DR-2026-08-04's own definition (retrievable without cloning) every identifier is still pre-publication; the identifier law has not bitten and names can still move. Second, the sealed group serves 518 documents from 12 of its 14 packages; removing the two benchmarking packages (96) and the two product-captured fixture trees named in the direction (14) leaves 408 documents across 10 packages, of which 5 are code-shaped files inside the golden execution-evidence fixture (the repository under test, its runner, two claim scripts) — fixture input data, not implementation.

This record settles the four things the direction left to this repository's process: how the mono consumes the spec, who produces the origin, what the catalog does with the benchmarking packages, and the destination of what remains.

## Decision

**0. The one amendment.** The protocol is authored and presented in `Jinn-Network/spec`. This repository is the TypeScript implementation of the protocol and the canonical Jinn network on Base; it consumes a pinned release of the spec and authors none of its documents. Everything else in DR-2026-07-30 stands.

**1. How the mono pins the spec release: vendor with provenance, guard by CI.** A sync script vendors every document of the pinned release into the packages' existing `schemas/`, `profiles/`, and `fixtures/` directories and commits them, with a provenance manifest recording the release tag, the release's manifest digest, and each file's sha256. The catalog carries the pin (tag, manifest digest, signing key id) and marks each vendored `publicSurface` as pinned; each such package's `authority` names the release, not this repository's design documents. CI fails if any vendored byte differs from the provenance manifest or the provenance manifest does not match the pinned release. Refresh is only "run the script with a new tag." Tarballs and package `exports` are unchanged.

"Keeps no editable copies" is read as MCP's TypeScript SDK reads it: the copy exists in git but is not authorable, because an edit cannot merge. Comparables checked 2026-09-03: MCP's SDK vendors the spec's schema from a pinned commit with a provenance manifest (commit, sha256, byte size) and commits it; Sigstore and in-toto publish generated bindings as packages from the spec repository (a pattern for generated code, not plain documents); Ethereum clients fetch consensus test vectors as pinned release tarballs into gitignored directories; OpenTelemetry JS and JSON Schema validators pin a submodule. In every case the pin is explicit, the digest recorded, and refresh a deliberate act. No comparable fetches runtime schemas at build time.

**2. Who produces the origin: the spec repository, and only it.** `spec.jinn.network` has one producer. It serves the documents records cite by identifier plus the conformance vectors the spec ships; implementation test fixtures are not served there, and this repository deploys nothing to it. Consequences: the protocol parts of the `implementations-v1` served group cross with the import (the discovery facts profiles minus the benchmark ones, the evidence repository bindings, the conformance-kit vectors for task execution and trust — about 90 documents on top of the 408); implementation fixtures stop being served and stay in their tarballs, the only place anything reads them; the build, sign, bundle, and local-serve scripts move to the spec repository, trimmed of their dependency on this repository's catalog (the release manifest is the inventory there); the live-host verifier stays here and checks that the origin serves the pinned release by manifest digest and signature; stable npm publication is gated on two facts — vendored bytes match the pin, and the origin serves the pin. #3308 (publish the host from CI) closes as moved.

Comparables checked 2026-09-04: MCP, SLSA, and the Ethereum EIPs deploy the origin from the spec repository; OpenTelemetry and JSON Schema deploy from one website repository that pins the spec repositories. In no inspected project does an implementation repository write to the spec's origin, or serve its test fixtures at any origin; conformance vectors live in a repository (the spec's or a conformance one) and travel as files or release assets.

**3. The benchmarking packages: re-labeled before the import.** The thirteen benchmarking packages (three in `sealed-platform-v1`, ten in `implementations-v1`) move to a release group owned by the benchmarking product: classification `product`, publish policy `canary-only`, not served at the protocol origin, dependencies allowed on both platform groups. One catalog-only chore PR, landing before the import, so the import is "everything the catalog calls sealed plus the protocol parts of the implementations group" with no exception list and the pin guard needs no carve-outs. The sealed group goes from fourteen packages to eleven. Four non-benchmarking packages depend on benchmarking ones (Colophon's `core` and `verify`, Policy Optimization, and the indexer on `benchmarking-records`); their groups must allow the new group. The layering law's tier-2 exemplar (the benchmark records) becomes historical; the architecture spec is not edited for it.

**4. The end state: five repositories; the mono is the workshop and is archived last.** The TypeScript SDK is the fifth extraction, into its own fresh repository through the same gate as the others, rather than what the mono "shrinks to." The end state is spec, TypeScript SDK, operator node, network (a deployment: contracts, addresses, staking and trust configuration, the venue binding), and products. The mono is the workshop from which each leaves through the gate — spec, then Colophon with the whole benchmarking domain, then the operator node, then the network, then the SDK — and is archived in place (public, read-only, front page pointing at the five) when the last has left. Nothing about the sequence changes; this names the destination of what remains, per the direction's own rule that every departure's destination is named in advance. The SDK repository's name is decided when it is created.

**The sequence, for the record.** (1) create `Jinn-Network/spec` with README and governance — done 2026-09-03; (2) this record; (3) re-label the benchmarking packages (#3910), then the byte-identical import and the generator move in the spec repository; (4) the spec repository's CI deploys the origin and the host repository is retired; (5) pin and vendor (#3911); (6) gate stable publication on the pin and retire this repository's host pipeline (#3912); (7) the normative text, written fresh for an outsider, released incrementally; (8) the conformance repository and a Python verifier written from the spec alone; (9) on the gate the stable release opens, the extractions in the order above. The legacy sweep runs independently throughout.

**The clean-repository rule** binds every step: only the protocol, its change mechanism (proposals and changelog), and its front door live in the spec repository. Never this repository's dated specs, decision records, plans, session prompts, transcripts, or architecture maps. The five families' design documents are sources for the writing and stay here. Normative text is written fresh, never copied.

## Alternatives considered and rejected

- **Build-time fetch into gitignored directories** for the vendored documents. No comparable does this for runtime schemas; it fits a test-time vector corpus later. Rejected for now.
- **A git submodule** at the release tag. The whole spec repository lands in the tree, clean-clone CI must recurse, and the copy step still exists.
- **A package published by the spec repository.** Sigstore's pattern, which applies to generated bindings; here the artifacts are plain JSON documents, and a publish pipeline is what the clean-repository rule keeps out.
- **Two producers into one origin** (the spec repository deploys its group; this repository keeps pushing the implementations group through a cross-repository credential, which is #3308 as written). No comparable; the host repository could not be retired; the leak persists.
- **A mono-owned origin for implementation fixtures.** No comparable serves implementation fixtures at any origin.
- **Leaving the benchmarking packages labeled sealed until the product extracts.** The catalog would contradict the direction, the pin guard would need exceptions, and stable publication would ship them under the platform's name.
- **Making the mono private.** No comparable develops in a private workshop exporting public mirrors; the issues, queue, autopilot, and decision records are public by design.

## Consequences

- **Follow-ups in this repository, as sub-issues of #3786, in order:** #3910 (chore, catalog re-label; Blocked on this record), #3911 (refactor, pin and vendor; Blocked on #3910 and the spec repository's first release), #3912 (chore, stable gate and pipeline retirement; Blocked on #3911). #3308 closes when #3912 lands.
- **Follow-ups in `Jinn-Network/spec`:** issue 1 (byte-identical import and the pipeline that builds the served root) and issue 2 (CI builds the attested bundle and deploys the origin; host repository archived). Three open items are recorded on issue 1 for the import to settle: whether the information-world record and the OCI repository binding, two record kinds outside the five families, cross as protocol; that code-shaped fixture inputs are data; that served paths keep their npm-scoped form in the first release.
- **Catalog and control.** The catalog schema gains the pin block and the `pinned` marker (#3911). `expectedPackageCount` on both platform groups changes and the generated topology is regenerated (#3910).
- **CI.** `platform-verification.yml` loses its build and sign steps; the stable live-host job verifies against the pin; two workflow-structure tests change with them; the signing key secrets move to the spec repository and this repository keeps the public key variables, re-pointed (#3912).
- **Runbooks.** The profile-hosting and stack-publishing runbooks are rewritten by #3912; the hand-refresh recipe is removed, not kept as break-glass, since this repository can no longer produce the bundle.
- **Nothing moves before its predecessor.** Every departure in step 9 still requires the extraction gate green and its own decision record, per the architecture spec §6.
