# anchor-kit-v1

Committed bytes for the anchor-evidence conformance kit
(`docs/superpowers/specs/2026-08-17-pluggable-integrity-providers-design.md` §11).

Almost nothing in this kit is static. The doctrine this package already follows —
executable builders over hand-synced JSON — applies with extra force to
cryptographic fixtures: a static token is a token nobody can regenerate, and a
kit of thirty hand-maintained tokens would drift out of agreement with itself
within one change. Everything the kit mints therefore comes from
`src/anchor-kit/`, deterministically, at test time.

Four files are here because they cannot be builders.

| File | Why it must be static |
|---|---|
| `token-digicert.der` | A real RFC 3161 token from a public authority, RSA-signed. No builder can produce production output; §11 requires the parser to be proven against it. Its bare `rsaEncryption` SignerInfo algorithm is the specific production fact the P1 allowlist exists to handle. |
| `token-sslcom.der` | The same, ECDSA-signed, from an independent authority. One RSA and one ECDSA capture is what §11 asks for. |
| `capture-provenance.md` | The endpoints, request profile, and payload the two captures came from. Provenance is not derivable from the bytes. |
| `cross-validation.md` | The §11 requirement that kit-minted tokens are validated once against an independent verifier. A transcript is a record of something that happened; it cannot be regenerated by the thing it validates. |

And one file exists to keep the transcript honest:

| File | Why it must be static |
|---|---|
| `kit-token-canonical.der` | The exact token `cross-validation.md` describes. The builders are deterministic, so this is normally identical to what they mint — but if a builder ever changes, a committed copy turns silent drift into a loud failure (`src/anchor-kit/real-tokens.test.ts`) instead of leaving a transcript that describes bytes nobody produces any more. |

Regenerate the canonical token with `yarn build && node
scripts/mint-anchor-kit-fixtures.mjs`; check it with `--check`. In normal
operation neither is needed, because the test asserts the same equality.

## Append-only, forever

These bytes are covered by the stack's fixture-immutability gate. A published
fixture is never edited: it is superseded by a new fixture plus a dated erratum
in `fixtures/manifest.sha256.json`. That is the whole reason the committed set is
five files rather than thirty — every static byte is a permanent commitment, and
a builder is not.

## Not here, deliberately

- **No authority trust roots.** The verifier ships with none (§8 step 3), so the
  captured tokens are exercised only on the no-trust-material path, where the
  honest outcome is `present`. The kit's own authority root is minted from a seed
  at test time and trusted only by the kit's own verifier configuration.
- **No OpenTimestamps proofs.** They are built deterministically by
  `src/anchor-kit/ots-builder.ts`, including the synthetic block headers that
  stand in for verifier-supplied chain material. A real chain-complete `.ots`
  proof arrives with the OpenTimestamps provider packet.
- **No bundles.** The §11 families that need an authenticated bundle snapshot —
  dangling anchors, kind mismatch, absence and declared-but-absence, the
  `closeAt` splice-catch, conflicting anchors, the matrix anchor, text
  conditionality — belong to the `integrity-anchors` check (§8) and to its own
  kit.
